# HTTP 오류 응답 설계 명세

다음 단계는 [정적 파일 설계](static-files-design.md)다. 정적 파일 단계에서는 GET 성공 응답을 파일 전송으로 확장한다.

[요구사항 명세](error-response-requirements.md)를 구현하기 위한 설계다. 아래 구현 방식은 **AI의 세부 설계 선택**이며, 코드에 반영하고 실행 검증했다.

## DS-009. 공통 오류 응답

- 입력: 오류 상태 코드.
- 처리: 정적 상태표에서 상태명을 찾고, 상태 줄은 `HTTP/1.1 코드 상태명`으로 만든다. `Content-Type: text/plain; charset=utf-8`, 본문 바이트 수인 `Content-Length`, `Connection: close`를 넣는다. 각 줄은 CRLF, 헤더와 본문 사이는 빈 줄로 구분한다.
- 결과: 본문에 상태명만 보내며 끝에 줄바꿈이나 문자열 종료 바이트는 보내지 않는다. 일부만 송신되면 남은 부분을 반복 전송한다.
- 확인 기준: 여섯 상태 모두 표와 본문이 일치하고 Content-Length가 실제 전송 본문 길이와 같다.

500 응답 자체에 추가 동적 할당이 필요하지 않도록 정적 문자열과 작은 스택 헤더 버퍼를 사용한다. 헤더 작성 길이도 검사한다. 이 응답 형식과 메모리 방식은 AI 설계 선택이다.

## DS-010. 파서 오류 응답

- 입력: `HTTP_PARSE_INVALID`, `HTTP_PARSE_TOO_LARGE`, `HTTP_PARSE_NO_MEMORY` 등 파서 결과.
- 처리: 각각 400·431·500에 대응한다. 수신 함수가 모든 실패를 `-1`로 합치지 않고 원인을 호출자까지 보존한다.
- 결과: `main()`이 원인에 맞는 오류 응답을 선택한다. 버전 미지원은 별도 결과로 구분한다.
- 확인 기준: 형식 실패·헤더 초과·할당 실패를 각각 유도했을 때 올바른 응답을 선택한다. 요청 줄부터 빈 줄까지의 기존 전체 헤더 제한 8192바이트를 유지한다.

## DS-011. 요청 수신 시간 제한

- 입력: `accept()` 성공 직후의 시각.
- 처리: `clock_gettime(CLOCK_MONOTONIC)`으로 종료 기한을 계산한다. 수신 전마다 남은 시간을 계산해 `poll()`로 해당 연결 하나의 읽기 준비를 기다린다. 준비되면 데이터를 읽고 다음 반복에서 잔여 시간을 다시 계산한다.
- 결과: 데이터 도착과 `EINTR` 재시도로 기한이 늘어나지 않는다. 기한 도달 시 헤더 미완성이면 시간 초과 결과를 반환한다.
- 확인 기준: 무응답·조각 수신·시스템 호출 중단 모두 동일한 총 10초 기한을 사용한다. 무기한 블로킹 수신으로 기한을 넘기지 않는다.

수신은 non-blocking 방식과 함께 사용해 준비 확인 후에도 무기한 막히지 않게 하고, 응답 단계에서 기존 송신 방식을 사용하도록 복원하는 설계다. `poll()`은 현재 연결 하나를 감시하며 동시 처리 기능을 추가하지 않는다. 응답 송신 시간 제한은 이번 범위가 아니다.

## DS-012. 미구현 메서드 응답

- 입력: 전체 헤더 파싱과 Host 검사에 성공한 요청.
- 처리: 메서드를 대소문자 구분해 `GET`과 비교한다. 같으면 기존 성공 응답, 다르면 501을 선택한다.
- 결과: `POST`·`get` 등 문법에 맞지만 현재 미지원인 이름은 501이다.
- 확인 기준: 잘못된 Host가 있는 POST 요청은 먼저 400을 받고, 정상 Host가 있는 POST 요청은 501을 받는다. 본문은 처리하지 않는다.

## DS-013. 미지원 버전 응답

- 입력: 완성된 요청 줄.
- 처리: 항목 구분·메서드 token·버전 문법을 먼저 검사한다. 버전은 `HTTP/` 뒤 ASCII 숫자 한 자리, 점, 숫자 한 자리인지 확인한다. 문법 실패는 400, 문법에 맞지만 `HTTP/1.1`이 아니면 별도 미지원 결과로 505를 선택한다.
- 결과: 문법 오류와 버전 미지원을 구분한다. 요청 줄 단계에서 505가 결정되면 추가 헤더를 기다리지 않고 응답 단계로 넘어간다.
- 확인 기준: `HTTP/1.0`은 505, `HTTP/abc`·누락 항목·잘못된 구분 공백은 400이다.

## DS-014. 연결과 자원 정리

- 입력: 처리 결과와 클라이언트 소켓.
- 처리: 성공 또는 선택된 오류 응답을 한 번 시도한다. 이후 성공·실패 모두 공통 정리 경로에서 요청 메모리를 해제하고 소켓을 닫는다.
- 결과: `main()`이 다음 `accept()`로 돌아간다. 송신 실패 시 다른 오류 응답을 재귀적으로 시도하지 않는다.
- 확인 기준: 수신·파싱·할당·송신 실패 후에도 자원 정리를 거쳐 다음 정상 요청을 처리한다.

수신 단절의 세부 정책은 다음과 같이 제안한다.

- 한 바이트도 받기 전에 EOF가 오면 응답 없이 정리한다.
- 요청 일부를 받은 뒤 EOF가 오면 불완전 요청으로 400을 시도할 수 있지만, 상대가 읽기를 유지하고 있다는 보장은 없다.
- 네트워크 수신 오류는 오류 응답을 강제하지 않고 정리한다. 시간 초과는 408을 시도하되 전달 불가능하면 정리한다.
- 초기화 실패는 기존처럼 로그와 프로세스 종료로 처리한다. 클라이언트 요청에 대한 500과 구분한다.

## 검증 결과와 한계

원인별 응답 형식과 정확한 본문, 기한 직전 완료·기한 경과 미완성, 조각 송수신, 단절·할당 실패·송신 실패 후 정리, 이후 GET 성공 응답을 확인했다. 파서 97개 검사, 응답 7종·부분 송신·EINTR·실패·기한 검사와 실제 TCP 테스트 12개가 통과했다. AddressSanitizer·UndefinedBehaviorSanitizer·누수 검사도 통과했다(파서·응답·수신 모듈 범위).
본문 관련 헤더 검증, 정적 파일·프록시 오류, 동시 처리, 송신 시간 제한은 후속 범위이며 완전한 HTTP 준수를 주장하지 않는다.

구현 파일: server.c(호출·정리), request_io.c/.h(수신 기한·오류 분류), http_request.c/.h(버전 오류 구분), http_response.c/.h(응답 생성·송신). 테스트용 컨테이너는 검증 후 종료했다. 부하 테스트는 실행하지 않았다.
