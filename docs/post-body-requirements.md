# POST 본문 수신 요구사항 명세

다음 6단계는 [keep-alive 요구사항](keep-alive-requirements.md)이다. 해당 단계를 적용하면 연결당 한 요청 후 종료하던 정책을 조건부 재사용으로 대체한다.

이번 5단계는 **POST 본문을 끝까지 받아 요청별 메모리에 보관하는 기능**이다. 구현했으며 검증 범위는 아래와 설계 문서에 기록한다.
구현 방법은 [설계 명세](post-body-design.md), 이전 단계는 [동시 처리 요구사항](concurrency-requirements.md)에 정리한다.

## 범위와 이전 단계 관계

기존 FR-001~028의 단계 기록은 유지한다. 이번에는 POST를 추가하고, GET은 기존 정적 파일 응답을 유지한다. epoll·pthread 역할 분담과 연결·큐 제한, 기존 오류 처리·종료 유예도 유지한다.
이번 단계는 연결당 한 요청을 처리한 뒤 닫는다. **다음 6단계는 keep-alive**이며 이번에 추가하지 않는다. JSON·폼 등 내용 해석, 동적 애플리케이션 처리, 프록시는 이후 범위다.

## FR-029. POST 완료 응답과 경로 범위

- 입력: 임의 경로의 문법·헤더 검사를 통과한 POST 요청.
- 동작: 본문을 모두 수신·보관한 뒤 204 No Content로 응답한다. 경로별 애플리케이션 처리나 파일 생성은 하지 않는다.
- 결과·완료 기준: `POST /a`, `POST /b` 모두 정상 수신 후 204다. 응답 본문·Content-Length·Transfer-Encoding은 없고 Connection은 close다. 본문을 반사해서 응답하지 않는다.

## FR-030. 본문 길이와 헤더 검증

- 입력: 수신한 모든 Content-Length(CL)·Transfer-Encoding(TE) 헤더.
- 동작: 이번에는 CL 방식만 지원한다. CL·TE가 모두 없거나 CL이 0이면 빈 본문이다. 헤더 이름은 대소문자를 무시해 찾는다. 헤더 목록의 원문·중복 보관 방식은 유지하되 본문 경계 검증을 추가한다.
- 결과·완료 기준: 다음 표대로 판정하고, 유효한 CL 길이만큼 수신한다.

| 입력 | 결과 |
| --- | --- |
| CL 한 줄의 비어 있지 않은 ASCII 십진 숫자 | 길이로 사용. 정상 범위의 값이 CLI 상한보다 크면 413 |
| CL 빈 값·부호·문자·쉼표 목록·표현 범위 오버플로 | 400 |
| CL 두 줄 이상 | 값이 같아도 400 |
| CL과 TE가 함께 있음 | 400. 둘 중 하나를 선택하지 않음 |
| TE 문법 오류 또는 최종 전송 코딩이 chunked가 아님 | 400 |
| 문법에 맞고 chunked로 끝나는 TE | 미지원이므로 501. 예: chunked 또는 gzip, chunked |

지원하지 않는 메서드의 기존 501 정책은 유지한다. GET에도 본문 경계 헤더를 검사하며, 정상 길이가 0이면 기존 파일 응답, 양수이면 이번에는 400으로 거절한다. GET 본문은 수신·처리하지 않는다.

## FR-031. 본문 보관과 경계

- 입력: 헤더 끝 뒤의 바이트와 유효한 본문 길이.
- 동작: 요청별 메모리에 원문 바이트와 실제 받은 길이를 보관한다. NUL과 개행을 포함해 변환하거나 잘라내지 않는다. CLI 본문 상한과 기존 8192바이트 헤더 상한은 별개다.
- 결과·완료 기준: 헤더와 본문이 한 번에 도착하거나 여러 번에 나뉘어도 정확한 바이트가 저장된다. 선언 길이 뒤 데이터는 본문에 넣거나 다음 요청으로 처리하지 않는다. 응답 뒤 연결을 닫는다.

## FR-032. 본문 수신 기한

- 입력: 헤더가 완성된 시각과 CLI 본문 총수신 시간.
- 동작: 헤더 완료 시각부터 본문 전체를 받을 총시간을 잰다. 본문 조각 수신이나 100 Continue 송신으로 기한을 연장하지 않는다.
- 결과·완료 기준: 기한 내 완료하면 204, 미완성이면 408을 시도한다. 기존 수락 후 헤더 총 10초는 유지하며 본문 기한과 구분한다. 본문 제한 시간을 임의로 10초로 고정하지 않는다.

## FR-033. Expect 처리

- 입력: Expect 헤더.
- 동작: 100-continue를 지원한다. 헤더·본문 길이·상한 등의 사전 검사를 통과하면 필요한 100 Continue를 보내고 본문을 받는다. 그 밖의 기대 값은 417로 거절한다. 사전 오류가 있으면 100 대신 최종 오류를 보낸다.
- 결과·완료 기준: 클라이언트가 100을 기다렸다가 본문을 보내도 정상 완료한다. 100은 임시 응답이며 이후 본문 오류에 400·408 등의 최종 응답을 보낼 수 있다.

## FR-034. 실패 응답

- 입력: 길이 검증·본문 수신·메모리 확보 결과.
- 동작: 아래 원인에 맞는 상태명 텍스트 오류 응답을 시도한 뒤 닫는다. 오류 본문·연결 정책은 기존 방식을 따른다.

| 원인 | 상태 |
| --- | --- |
| 본문 선언 길이가 CLI 상한을 넘음 | 413 Content Too Large |
| 잘못된 길이·중복 CL·충돌하는 길이 헤더·미달 EOF | 400 Bad Request |
| 본문 수신 기한 초과 | 408 Request Timeout |
| 본문 메모리 확보 실패 | 500 Internal Server Error |
| 미지원 전송 방식·메서드 | 501 Not Implemented |
| 미지원 Expect 값 | 417 Expectation Failed |

- 결과·완료 기준: 선언한 길이를 다 받기 전에 전송을 끝내면 성공으로 처리하지 않는다. 이미 끊긴 상대에게 응답 전달을 보장하지 않으며, 송신 불가 시 자원 정리 후 닫는다.

## FR-035. CLI와 실행 스크립트

- 입력: `./server 포트 루트 워커수 큐상한 연결상한 본문최대바이트 본문총수신초`의 일곱 필수 인자.
- 동작: 본문 상한은 바이트, 본문 기한은 초 단위로 받는다. start.sh의 PORT·ROOT·WORKERS·QUEUE_LIMIT·CONNECTION_LIMIT·BODY_LIMIT·BODY_TIMEOUT 변수로 설정해 같은 인자를 서버에 전달할 수 있게 한다. server.conf 파서는 추가하지 않는다.
- 결과·완료 기준: 직접 실행과 스크립트 실행이 같은 설정으로 동작한다. 잘못된 값이나 누락은 시작 전에 거절한다.

`8080 ./public 4 64 100 1048576 30`은 스크립트에 둘 수 있는 **AI 초기 설정 예시**다. 사용자 필수 수치나 서버의 생략 기본값이 아니다.

## FR-036. 기존 기능과 자원 정리

- 입력: 동시 POST·GET, 성공·실패·단절·종료.
- 동작: 본문 수신은 이벤트 루프에서 non-blocking으로 처리하고 다른 연결을 계속 관리한다. 받은 본문은 해당 요청 처리까지 유지하고 모든 종료 경로에서 해제한다.
- 결과·완료 기준: 다른 요청의 본문이 섞이지 않고 요청 메모리가 누수·중복 해제되지 않는다. GET 정적 파일·오류 응답·동시 처리·시간 제한·종료 유예가 계속 동작한다.

## 결정과 검증 상태

경로·204·CL 지원 범위·헤더 오류 정책·메모리 원문 보관·CLI 상한과 기한·Expect·GET·추가 데이터·start.sh는 사용자 결정이다. 구체 자료 구조·경계 전달·응답 상태 분리는 [AI 세부 설계](post-body-design.md)에 기록한다.
CLI 설정의 상한만큼 요청별 메모리를 사용할 수 있으므로 동시 연결 수와 함께 설정해야 한다. 이번 단계에 별도의 전역 본문 메모리 상한은 추가하지 않는다.
본문 검증·원문 보관·할당 실패·임시 응답 부분 송신 단위 검사와 기존 단위 검사, ASan·UBSan·누수 검사를 통과했다. 실제 TCP POST 13개 시나리오는 일반 빌드와 전체 서버 sanitizer 빌드 모두 통과했다. 기존 정적 TCP 15개·오류 TCP 12개·동시 TCP 10개도 통과했다. Docker 이미지 빌드와 이미지 안의 start.sh 기동·POST 204 응답도 확인했다. 처리량 부하 측정은 이번에 수행하지 않았다.
