## DS-054. 환경과 측정 경계

실행 전에 OS·Docker/커널·이미지·컴파일러·도구 버전, 커밋·미커밋 변경, CPU/RAM 제한, 실제 가용 자원과 모든 CLI/start.sh 설정을 보관한다. 현재 환경을 기준으로 조건 중간에 워커 수·큐·연결 상한·기한을 바꾸지 않는다.
생성기·대상 서버·각 백엔드의 배치와 CPU/RSS를 별도로 기록한다. 백엔드를 같은 요청으로 직접 측정해 용량 부족이나 생성기 포화를 프록시 장애와 혼동하지 않는다. 사전 용량 확인은 정식 측정에서 분리한다.

측정 경계는 생성기의 요청 시작부터 응답 완료까지이며 접속 대기와 백엔드 처리를 포함한다. keep-alive를 켠 조건을 기준으로 실제 재사용률·연결 수·최대 요청 수에 따른 재접속을 기록한다. 짧은 예비 실행 뒤 따뜻해진 OS 파일 캐시를 기준으로 하며 cold-cache 측정이라고 주장하지 않는다.

선택 이유·대안: 기존 Docker 환경은 준비 비용이 낮고 재현하기 쉽다. 별도 부하 발생 호스트보다 CPU·네트워크 경합이 커서 서버 단독의 절대 처리 한계라고 해석할 수 없는 비용을 감수한다.

## DS-055. 정상 부하 측정

반복 가능한 고정 바이트를 준비한다. 아래 크기·비율은 AI의 시작안이며 실제 준비값과 해시를 결과에 기록한다.

| 시나리오 | 구체 워크로드 제안 |
| --- | --- |
| 정적 단독 | 4KiB 텍스트와 1MiB 바이너리를 동일 요청 수로 배분 |
| 프록시 단독 | 결정적 응답을 주는 HTTP 백엔드 2개. GET 1KiB 응답·POST 1KiB 바이너리/결정적 응답을 동일 요청 수로 배분 |
| 혼합 | 요청 수 기준 정적 50%·프록시 50%, 각 내부 구성은 위와 같음 |

동시 수는 outstanding 클라이언트 요청 수로 정의한다. 1·10·50·100 각각 예비 5초 후 정식 30초를 3회 실행하는 안이다. 분산·파일·본문 크기·생성기 제한 시간을 반복 중 고정하고 실행 순서와 회차 간 회복 상태를 기록한다. 워크로드별 MIME·상태·길이·기대 본문을 미리 정한다.
설치돼 있고 기능이 맞는 부하 도구를 먼저 확인한 뒤 선택한다. RPS·지연 분포·다양한 요청·오류를 수집할 수 있는 도구를 우선한다. 부하 검사에서 빠진 본문 검증은 동일 동시 조건의 별도 기능 검사로 보완하며 상태 코드만 확인하고 내용까지 검증했다고 보고하지 않는다.

선택 이유·대안: 고정 입력은 회차 편차와 회귀를 비교하기 쉽다. 실제 사용자 트래픽 전체를 재현하는 방식보다 단순하지만 한정된 크기·비율의 결과라는 비용을 명시한다. 30초 종료 후 미완료 요청도 기록하며 조용히 성공 집계에서 제외하지 않는다.

## DS-056. 과부하와 지속 부하

동시 200은 세 시나리오별로 정상 부하와 같은 30초 3회 형식을 제안하되 별도 과부하 표로 남긴다. 기존 연결 상한·큐·시간 설정을 높여 실패를 숨기지 않는다. 종료 후 동시 1의 정확성 요청으로 회복·자원 회수를 확인한다.
10분 지속 부하는 혼합 시나리오·동시 50을 시작안으로 사용한다. 실제 정상 한도가 그보다 낮다면 실패 사실을 먼저 남기고, 안정성 추적용 부하를 별도 조건으로 낮춰 실행한다. 낮춘 결과를 원래 조건 통과로 바꾸지 않는다.
예비와 회차 종료 뒤 진행 요청이 끝나거나 기한 처리로 정리됐는지 확인한다. 로그/RSS 증가를 캐시·할당기 보유와 실제 누수 증거로 구분한다.

선택 이유·대안: 200은 거절·회복을, 10분은 시간에 따른 변화를 보기 위한 범위다. 장시간 운영·수천 연결 검사보다 비용이 작지만 하루 이상 안정성이나 C10K를 입증하지는 못한다.

## DS-057. 장애와 회복 검증

운영망이 아닌 Docker 격리 네트워크에서 한 장애씩 주입하고 종료 후 설정을 복구한다. 실제 SYN을 버리는 통제된 규칙으로 접속 timeout을 재현해 즉시 거절과 구분한다. 규칙·패킷 또는 동등한 접속 증거·발생 시간을 남긴다. 안전하게 재현할 권한·도구가 없으면 미실행으로 보고한다.

| 장애 | 확인할 동작 |
| --- | --- |
| 백엔드 중지/접속 거절 | 요청 전 실패 502, 다른 백엔드 자동 재시도 없음 |
| SYN drop | 실제 접속 기한 뒤 504, 무한 대기 없음 |
| 응답 무진행/요청을 읽지 않는 백엔드 | 설정한 구간의 기한·실패 상태, 작업·소켓 회수 |
| 잘못된 헤더/잘못된 chunk/응답 중단 | 최종 응답 전 502, 시작 뒤 종료. 정상 백엔드 4xx/5xx와 구분 |
| 클라이언트 수신 중단/단절 | 백프레셔·송신 기한·upstream 정리, 다른 연결 진행 |
| 과부하 해제·백엔드 재시작 | 기존 정책 유지, 이후 정상 요청 회복 |
| idle·진행 요청 중 SIGTERM | 새 수락 중단·idle 정리·기존 유예 완료/기한 종료 |

백엔드 자체 오류·용량 부족·테스트 주입 오류를 프록시 버그와 구분하고, 재현이 틀렸으면 수정 후 다시 확인한다. 회복은 단순 프로세스 생존이 아니라 정확한 후속 응답과 FD·연결 정리로 확인한다.

선택 이유·대안: 통제된 실제 네트워크 장애는 함수 대체 검사보다 운영 경로 증거가 강하다. 환경 준비와 권한이 필요하며 재현하지 못한 상황을 유사 장애 통과로 대신하지 않는 비용을 감수한다.

## DS-058. 응답·메모리·경합 검증

기존 파서·POST·keep-alive·정적·프록시·동시 상태 회귀를 먼저 실행한다. 바이너리 해시·상태·Content-Length 또는 chunk 경계·응답 순서·유사 경로 라우팅·서로 다른 요청 내용 혼입을 확인한다. 긴/부분 수신, 100 Continue, 요청 재사용과 실패 후 정상 요청도 포함한다.
성능 측정은 최적화 일반 빌드로 하고 ASan·UBSan·누수 검사는 별도 빌드에서 병렬·과부하·단절·종료를 실행한다. 성능 수치에 sanitizer 결과를 섞지 않는다.
TSan은 별도 빌드로 재시도한다. 기존 unexpected memory mapping 등으로 시작하지 못하면 전체 오류 출력·이미지/커널·명령·시도 범위를 보관하고 경합 검증 미완료라고 적는다. 실행된 경우에는 경합 경고를 실패로 처리한다.

선택 이유·대안: 기능·안전성 검사를 부하 도구의 상태 코드 검사와 분리해 누락을 보완한다. 검사가 늘고 sanitizer와 일반 빌드 간 실행 조건 차이가 생기지만, sanitizer로 처리량을 대표하는 잘못된 비교를 피한다.

## DS-059. 측정 지표와 판정

회차별 총 요청·완료·성공·예상 오류·예상 밖 오류·미완료, 유효 측정 시간과 RPS, p50/p95/p99를 보존한다. 3회 원시 지연 표본을 합칠 수 없으면 p99를 단순 평균해 전체 p99라고 하지 말고 회차별 값과 범위를 제시한다.
서버·백엔드·생성기의 CPU/RSS를 구분하고 서버 FD·스레드 수를 예비 전·진행 중·정리 후에 수집한다. 시계열 기본 주기는 1초를 제안한다. 수집 자체의 오버헤드·측정 실패도 기록한다.
정상 부하에서 정확성 실패·예상 밖 오류 하나라도 있으면 실패다. 과부하 503·backlog 접속 거절도 관련 상한·로그 증거와 맞을 때 정책 결과로 분류한다. 이유 없는 timeout·요청 deadline 초과·도구 오류를 정상 과부하로 일괄 처리하지 않는다. 최종 응답 일부만 받은 요청은 성공이 아니다.
크래시·누수·invalid memory·정책 위반·회복 실패는 수정 필요다. 실행 불가·응답 검증 부족·TSan 시작 실패는 미완료다. 미완료를 통과에 포함하지 않으며 실패를 남긴 상태에서 전체 검증 완료라고 보고하지 않는다.

선택 이유·대안: 최소 성능 숫자를 미리 정하는 합격 검사 대신 실제 용량·변동을 기록한다. 환경에 맞지 않는 성능 보장을 피하지만 숫자만으로 운영 용량을 확정할 수 없고 안전 여유도 별도 판단해야 한다.

## DS-060. 결과와 검증 한계 기록

결과는 validation-results/실행시각 같은 별도 경로에 환경·명령·stdout/stderr·도구 원본·자원 시계열·오류 증거·요약표를 보관하는 안이다. 이번 문서 작업에서는 결과 폴더·스크립트·테스트를 생성하지 않는다.
보고서에는 조건별 3회 결과·범위, 과부하와 정상 부하 분리, 지속 부하 자원 추이, 장애별 기대/실제/회복, PASS/FAIL/미완료와 재검사 필요사항을 넣는다. 도구가 보고한 RPS와 검증 완료 요청 기준을 구분하고 비정상 회차를 제외하면 이유와 원본을 남긴다.
포트폴리오에는 Docker 자원·파일/API 크기·백엔드 수·캐시·keep-alive·호스트 경합·TSan 한계와 재현 명령을 함께 싣는다. 10분·동시 200 결과로 24시간 안정성·모든 트래픽·서버 단독 최대 성능을 주장하지 않는다.

선택 이유·대안: 요약 숫자만 남기는 것보다 검토와 재현이 쉽다. 로그 보관·분류 비용이 들지만 성공 사례만 고른 설명과 미검증 주장을 피할 수 있다.
