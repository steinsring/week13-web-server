# HTTP 오류 응답 요구사항 명세

이번 단계는 **오류에 맞는 HTTP 응답을 보내는 기능**이다. 요구 범위는 확정했으며, 구현했으며 아래 검증 결과를 확인했다.
구현 방법은 [설계 명세](error-response-design.md), 이전 동작은 [파싱 요구사항](http-parser-requirements.md)에 정리한다.

다음 단계는 [정적 파일 요구사항](static-files-requirements.md)이다. 그 단계를 적용하면 GET의 고정 `hello world`를 파일 응답으로 대체한다.

## FR-009. 공통 오류 응답

- 입력: 처리 중 확인한 오류 종류.
- 동작: 해당 상태 코드와 아래 상태명을 사용한다. 본문은 간단한 텍스트 상태명만 보내며 구체적인 내부 원인은 보내지 않는다.
- 결과: 클라이언트가 상태 코드와 본문을 확인할 수 있다.
- 완료 기준: 각 오류의 코드·상태명·본문이 아래 표와 일치한다. 성공 응답은 기존대로다.

| 상태 코드 | 상태명과 본문 |
| --- | --- |
| 400 | Bad Request |
| 431 | Request Header Fields Too Large |
| 500 | Internal Server Error |
| 408 | Request Timeout |
| 501 | Not Implemented |
| 505 | HTTP Version Not Supported |

## FR-010. 파서 오류 응답

- 입력: 요청 파싱 결과.
- 동작: 잘못된 요청 형식은 400, 전체 요청 헤더의 기존 8192바이트 제한 초과는 431, 메모리 확보 실패는 500으로 구분한다.
- 결과: 기존의 무응답 종료 대신 오류 응답을 시도한다.
- 완료 기준: 잘못된 요청 줄·Host 누락은 400, 헤더 제한 초과는 431, 헤더 목록 할당 실패는 500이다. HTTP 버전 오류는 FR-013을 적용한다.

## FR-011. 요청 수신 시간 제한

- 입력: 연결 수락 시점과 요청 헤더 수신 상태.
- 동작: 연결을 수락한 직후부터 총 10초 안에 전체 헤더를 받아야 한다. 데이터가 조금씩 오거나 시스템 호출이 중단돼도 제한 시간을 다시 시작하지 않는다.
- 결과: 제한 시간 안에 헤더가 완성되지 않으면 408 응답을 시도한 뒤 연결을 닫는다.
- 완료 기준: 10초 전에 헤더가 완성되면 처리하고, 기한까지 미완성이면 408 경로로 간다. 조각 데이터를 계속 보내도 기한이 늘어나지 않는다.

## FR-012. 미구현 메서드 응답

- 입력: 헤더와 Host 검사까지 성공한 요청의 메서드.
- 동작: 대문자 `GET`만 현재 지원한다. 그 밖의 문법에 맞는 메서드는 501로 처리한다.
- 결과: `GET`은 기존 성공 응답, `POST`·`get`·`CUSTOM`은 501이다.
- 완료 기준: 잘못된 형식의 메서드는 400이며, 지원하지 않는 메서드라도 Host가 잘못됐다면 501보다 파싱 오류를 먼저 처리한다.

POST 본문을 받거나 실행하는 기능은 후속 단계다.

## FR-013. 미지원 버전 응답

- 입력: 문법 검사를 마친 요청 줄의 HTTP 버전.
- 동작: 문법은 `HTTP/숫자 한 자리.숫자 한 자리`로 구분한다. `HTTP/1.1`만 지원하며 문법에 맞는 다른 버전은 505로 처리한다. 버전 문법 자체가 잘못되면 400이다.
- 결과: `HTTP/1.0`은 505, `HTTP/abc`는 400이다.
- 완료 기준: 요청 줄의 항목 누락·구분 공백·메서드 문법 등이 잘못되면 버전 지원 여부를 판단하기 전에 400으로 처리한다.

## FR-014. 연결과 자원 정리

- 입력: 성공·오류·수신 단절·송신 실패 중 하나로 끝난 요청.
- 동작: 오류 응답에는 연결 종료를 알린다. 응답 시도 후 해당 연결과 요청 자원을 정리하고 다음 연결을 기다린다.
- 결과: 한 요청의 실패가 이후 정상 요청을 막지 않는다.
- 완료 기준: 부분 송수신과 모든 실패 경로에서도 자원을 정리하며, 다음 연결에 기존 성공 응답을 보낼 수 있다.

이미 끊긴 연결 등에는 응답 전달을 보장할 수 없다. 송신 실패 후 다른 오류 응답을 반복해서 보내지 않는다. 서버 시작 중 `socket()`·`bind()` 등이 실패하면 응답할 클라이언트가 없으므로 로그를 남기고 프로세스를 종료한다.

## 사용자 결정과 설계 선택

여섯 오류의 범위, 상태명만 담은 텍스트 본문, 전체 수신 시간 10초, GET만 지원하는 정책은 사용자 결정이다. 8192바이트는 기존 제한을 유지한 값이다.
세부 응답 형식·반환값·시간 측정·단절 시 처리는 [AI 설계 선택](error-response-design.md)에 구분한다.

이 단계도 완전한 HTTP 검증을 뜻하지 않는다. `Content-Length`·`Transfer-Encoding`의 값·중복·상호관계 검증은 본문 처리 단계로 미룬다.

## 검증 결과

여섯 오류별 상태·헤더·정확한 본문, 시간 제한 전후와 조각 수신, 부분 송신, 연결 단절, 할당 실패 시 정리와 다음 정상 연결을 확인했다. 실제 TCP 테스트 12개가 통과했다.

구현 파일: server.c(호출·정리), request_io.c/.h(수신 기한·오류 분류), http_request.c/.h(버전 오류 구분), http_response.c/.h(응답 생성·송신). 테스트용 컨테이너는 검증 후 종료했다. 부하 테스트는 실행하지 않았다.
