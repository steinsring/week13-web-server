# Keep-alive 설계 명세

## 선택 이유와 트레이드오프

순차 처리·잔여 데이터 보관·설정 가능한 idle/횟수 제한·완전 수신 403/404 재사용은 사용자와의 문답으로 확정했다. 아래 표는 그 이유와 기술적 비교를 정리한 것으로, 세부 비교 전체를 사용자가 직접 제안했다는 뜻은 아니다. HTTP 응답 순서·길이 제약과 조절 가능한 운영 정책도 구별한다.

| 대응 설계 | 선택과 이유 | 비교 대안 | 얻는 점 | 감수한 점 |
| --- | --- | --- | --- | --- |
| DS-037 | HTTP/1.1 연결을 기본 재사용하고 close 요청을 존중한다. | 항상 한 응답 후 닫기 | 반복 요청의 TCP 연결 생성 비용을 줄인다. | 응답 길이·요청 경계를 정확히 관리하고 idle 연결도 자원으로 계산해야 한다. |
| DS-038 | 같은 연결에서는 응답 후 다음 요청을 순차 처리한다. | 여러 요청 작업을 병렬 실행하고 순서대로 응답 | Connection의 요청·작업·송신 상태를 하나씩 관리한다. 서로 다른 연결의 기존 동시성은 유지한다. | 뒤 요청은 느린 앞 응답을 기다린다. HTTP/1.1의 응답 순서는 지켜야 하지만 내부 작업까지 순차일 필요는 없으며, 이 부분은 복잡성을 줄이려는 선택이다. |
| DS-038 | 이미 받은 다음 요청은 유한 pending에 보관하고 응답 중 추가 수신을 멈춘다. | 잔여 데이터 폐기·무제한 파이프라인 적재 | 유효한 다음 요청을 잃지 않으며 사용자 공간 메모리를 제한하고 TCP 흐름 제어를 활용한다. | 클라이언트의 추가 송신이 대기할 수 있고, 다음 요청을 미리 파싱·작업하지 않는다. |
| DS-039 | 응답 후 idle을 따로 제한하고 첫 바이트부터 헤더 제한으로 전환한다. | 연결 무기한 유지·idle과 헤더에 같은 기한 사용 | 사용하지 않는 연결을 회수하면서 새 요청의 수신 시간을 구분한다. | 상태·기한 전환이 추가되고 드문 요청은 재연결이 필요하다. 10초는 사용자 승인 초기 설정이며 성능 측정의 최적값은 아니다. |
| DS-040 | 연결당 최대 요청 수도 설정한다. 계속 요청하면 idle만으로는 닫히지 않기 때문이다. | 횟수 제한 없이 idle만 적용 | 사용 중인 연결도 일정 횟수 뒤 정리할 기회를 얻는다. | 자주 쓰는 정상 클라이언트도 재연결해야 한다. 새 연결의 공정한 진입이나 재접속 공격 방지를 보장하는 정책은 아니다. 100회는 변경 가능한 사용자 승인 초기값이다. |
| DS-041 | 완전히 수신한 403·404 뒤에는 유지하고 경계가 불명확하거나 그 밖의 닫기 정책 오류는 종료한다. | 모든 오류에서 종료·모든 오류에서 유지 | 정상 요청의 파일 처리 오류 때문에 재연결하지 않으면서 불명확한 잔여 바이트의 오해석을 피한다. | 수신 완료 여부와 상태를 함께 판단해야 한다. 500·503 등까지 닫는 것은 모든 오류에서 종료해야 한다는 규칙이 아니라 보수적 AI 설계 정책이다. |
| DS-042 | idle·횟수를 CLI와 start.sh에서 지정한다. | 코드에 상수 고정 | 재빌드 없이 실행 환경에 맞게 조절한다. | 인자·문서·Docker 설정을 함께 맞춰야 한다. 필수 CLI 인자와 스크립트 초기값은 서로 다른 개념이다. |
| DS-043 | 요청 자원만 리셋하고 연결·횟수·pending은 유지한다. 늦은 결과에는 세대와 요청 순번을 확인한다. | 연결 전체 재생성·상태를 무조건 유지 | 재사용 비용을 줄이면서 요청 간 데이터 혼입을 막는다. | 초기화 대상과 유지 대상을 빠짐없이 나눠야 하며 작업 실행 중 수명을 보장해야 한다. |
| DS-043 | 종료 시 idle은 즉시 닫고 진행 요청만 기존 유예 안에 마친다. | 모든 연결 즉시 종료·유지 연결의 새 요청까지 계속 허용 | 진행 응답을 마칠 기회를 주면서 서버 종료가 계속 미뤄지지 않게 한다. | 대기하던 클라이언트는 재접속해야 하고 유예 초과 응답은 중단된다. |

## DS-037. 연결 재사용과 종료 요청

- 입력: 모든 Connection 헤더와 요청 상태.
- 처리: 이름과 쉼표 구분 토큰을 대소문자 무시로 비교하고, 어느 항목에든 close가 있으면 종료를 우선한다. HTTP/1.1은 기본 유지하며 유지 시 Connection: close를 보내지 않는다. 선택 사항인 Keep-Alive 응답 헤더는 추가하지 않는다.
- 결과·확인 기준: 응답 생성 전에 종료 여부를 결정해 파일·301·204·오류 헤더 생성에 전달한다. 송신한 헤더는 바꾸지 않는다. 응답 경계가 명확할 때만 재사용하며 204·100에 길이 헤더를 추가하지 않는다.

## DS-038. 순차 처리와 잔여 데이터

- 입력: 현재 수신 버퍼와 파서·본문 수신기가 소비한 길이.
- 처리: 현재 요청 경계까지 소비하고 나머지는 연결 소유의 잔여 버퍼에 남긴다. 최종 응답 완료 전에는 다음 요청을 파싱·작업 큐 제출하지 않는다. 이미 읽은 잔여 바이트를 넘어서 계속 소켓을 비우지 않는다.
- 결과·확인 기준: POST 본문 뒤 GET, 두 GET, 다음 헤더의 일부만 남은 경우 모두 다음 차례에 정확히 이어 처리한다.

추가 대기 공간은 기존 한 번의 유한 수신 조각 크기 이내로 관리하는 안을 사용한다. 무제한 파이프라인 목록을 만들지 않고, 응답 중에는 EPOLLIN 관심을 내려 커널의 흐름 제어를 사용한다. 잔여 데이터의 소비 위치를 기록해 요청별 버퍼 초기화와 분리한다.
최종 응답이 끝나면 재사용 조건을 확인하고, 유지할 때만 잔여 데이터를 다음 파서에 공급하거나 EPOLLIN을 다시 등록한다. close 정책이면 남은 요청을 실행하지 않는다.

## DS-039. 다음 요청 대기 시간

- 입력: 최종 응답 완료 시각과 CLOCK_MONOTONIC 시각.
- 처리: 잔여 데이터가 없으면 idle 마감을 한 번 정한다. idle 만료는 응답 없이 닫는다. 다음 요청의 첫 바이트를 받으면 idle을 끝내고 기존 헤더 총 10초를 시작한다.
- 결과·확인 기준: 첫 연결은 기존 accept 직후 헤더 10초다. 재사용 연결은 idle 시간과 다음 헤더 수신 시간을 분리하며 조각 수신으로 헤더 기한을 갱신하지 않는다.

이미 보관한 요청 데이터는 앞 응답 완료 후 처리 차례가 왔을 때 헤더 기한을 시작한다. 서버가 앞 요청을 처리한 시간을 다음 요청의 수신 지연으로 계산하지 않는다. 헤더 완료 후의 본문 총기한, 파일 작업 대기·송신 무진행 제한은 기존 규칙을 따른다.

## DS-040. 연결별 최대 요청 수

- 입력: 완료한 최종 응답 수와 이번 요청의 순번.
- 처리: 이번 순번이 N이면 헤더를 보내기 전에 close를 정한다. 임시 100은 세지 않고 최종 응답 한 개를 요청 한 회로 센다. 재사용 가능한 403·404도 횟수에 포함한다.
- 결과·확인 기준: N=1은 매번 한 요청 후 종료하고, N번째 응답은 close다. 버퍼에 N+1번째 요청이 있어도 실행하지 않는다.

## DS-041. 오류 뒤 재사용

- 입력: 최종 상태, 본문 포함 요청 수신 완료 여부, 응답 전송 결과.
- 처리: 정상 200·204·301과 완전 수신 403·404만 재사용 가능한 안을 제안한다. 400·408·413·417·431·500·501·503·505 및 송수신 실패는 닫는다. 500·503 등의 종료는 사용자 추가 확정이 아닌 보수적 설계 제안이다.
- 결과·확인 기준: 오류 문구만 보고 유지하지 않고 요청 경계·최종 응답 완료를 함께 확인한다. close 요청·횟수 제한·서버 종료가 있으면 재사용 가능한 상태도 닫는다.

GET 본문 양수 거절 등 읽지 않은 본문이 남는 오류 뒤에 다음 파싱을 시작하지 않는다. 응답 시작 후 파일 읽기·송신 실패도 연결만 정리한다. 100 이후의 최종 오류는 기존 임시/최종 응답 분리를 유지한다.

## DS-042. 실행 설정

- 입력: 기존 일곱 필수 인자와 idle 초·최대 요청 수.
- 처리: 기존 인자 뒤에 idle_timeout_seconds·max_requests를 붙여 아홉 필수 인자로 받는 안을 사용한다. start.sh에는 KEEP_ALIVE_TIMEOUT=10, KEEP_ALIVE_MAX_REQUESTS=100을 추가해 전달한다. 변수 이름과 위치는 AI 세부 설계다.
- 결과·확인 기준: 양의 정수·표현 범위·시간 계산 넘침을 시작 전에 검증한다. 초기 10초/100회는 실행 설정으로 변경 가능하고 서버의 생략 기본값으로 사용하지 않는다.

## DS-043. 요청 자원과 서버 종료

- 입력: 응답 완료와 다음 요청 시작 또는 연결 정리.
- 처리: 이전 헤더 목록·본문·파일·전송 버퍼·요청 타이머를 정리하고 요청 상태를 초기화한다. 소켓·연결 식별자·요청 횟수·잔여 데이터는 유지한다. 내부 문자열 포인터가 있는 요청 구조체를 이동·값 복사하지 않는다.
- 결과·확인 기준: 이전 요청 값이 다음 요청에 남지 않는다. 작업 결과에는 연결 세대와 요청 순번을 함께 확인해 늦은 결과가 다음 요청을 덮어쓰지 못하게 한다. 기존 worker 실행 중 수명 보장을 유지한다.

종료 시 idle 연결은 즉시 닫고, 진행 중 요청만 기존 최대 10초 유예로 마무리하는 안을 사용한다. 그 연결의 버퍼에 남아 있는 다음 요청은 새로 시작하지 않는다. 아직 헤더를 보내지 않았다면 close를 표시하고, 이미 보낸 헤더는 바꾸지 않고 처리 뒤 닫는다. 신호로 기한을 연장하거나 수락 감시를 다시 켜지 않는다.

## 검증 계획과 상태

`tests/test_keep_alive.py`의 실제 TCP 13개가 통과했다. GET/POST·빈 204의 반복, POST 본문 뒤 GET과 부분 다음 헤더, 4096바이트를 넘는 파이프라인, 큰 응답 순서와 다른 연결 병행, 403/404·301 재사용, 복수 Connection 헤더·close 우선, N번째 종료·100 횟수 제외, idle 만료·새 헤더 기한 분리, idle의 연결 상한 포함, 반복 요청의 FD 회수와 종료 중 다음 요청 중단을 확인했다.

`make all test sanitize`도 통과했다. 전체 서버 ASan·UBSan·누수 빌드에서 keep-alive 13개와 POST 13개가 통과했다. 오류 TCP 12개·정적 TCP 15개·동시 TCP 10개는 최대 요청 수 1로 이전 정책을 재현해 회귀 검사했다. 파서·본문·응답·정적 파일·동시 상태 단위 검사와 기존 종료 유예 검사를 유지했다.

Docker 이미지 빌드, 이미지의 start.sh 실행, curl의 같은 연결 재사용과 SIGTERM 정상 종료를 확인했다. TSan과 처리량 부하 측정은 이번 단계에서 실행하지 않았다. 강제 프로세스 종료 경로는 정상 종료의 누수 검사와 구분한다.
