# 리버스 프록시 요구사항 명세

이번 7단계는 **실행 중인 백엔드에 요청을 전달하고 응답을 중계하는 기능**이다. 동적 요청 처리와 과제의 리버스 프록시 구현을 이 방향으로 진행한다.
사용자 요구 범위는 확정했다. 구체 프레이밍·헤더·상태 운용은 [설계 명세](reverse-proxy-design.md)의 AI 설계안과 구분한다. FR-044~053을 구현했으며 마지막 절에 실제 검증 범위를 기록한다.
이전 단계는 [keep-alive 요구사항](keep-alive-requirements.md)이다. 기존 FR-001~043의 단계 기록은 유지한다.

## 확정 요구사항

각 FR은 [설계 명세](reverse-proxy-design.md)의 같은 번호 DS와 1:1로 대응한다.

| 요구사항 | 대응 설계 |
| --- | --- |
| FR-044. 경로 기반 전달 | DS-044 |
| FR-045. 전달 메서드 범위 | DS-045 |
| FR-046. 백엔드 목록과 분산 | DS-046 |
| FR-047. 백엔드 연결과 재시도 | DS-047 |
| FR-048. 응답 스트리밍 | DS-048 |
| FR-049. 클라이언트 연결과 기존 기능 | DS-049 |
| FR-050. 리다이렉트 주소 변환 | DS-050 |
| FR-051. 백엔드 기한 설정 | DS-051 |
| FR-052. 시작 설정과 주소 해석 | DS-052 |
| FR-053. 실패 응답과 자원 정리 | DS-053 |

## FR-044. 경로 기반 전달

- 입력: 클라이언트 요청 경로와 쿼리 문자열.
- 동작: 파서가 보관한 **원문 경로** 기준으로 `/api`와 `/api/*`를 전달한다. 디코딩·정규화 후 라우팅하지 않는다. 접두사와 쿼리 원문을 유지한다.
- 결과·완료 기준: `/api/users?page=1`은 백엔드에도 같은 요청 대상으로 전달된다. `/apix`처럼 경계가 다른 경로는 프록시 경로에 포함하지 않는다. 그 밖의 경로는 기존 서버 처리로 이어진다.

## FR-045. 전달 메서드 범위

- 입력: 프록시 경로에 해당하는 요청 메서드.
- 동작: **이번에는 GET과 POST만 전달한다.** 다른 메서드는 후속 확장 범위로 남긴다.
- 결과·완료 기준: GET·POST가 백엔드에 전달되고 그 응답이 클라이언트로 중계된다. 프록시 POST는 기존 고정 204 처리를 대신한다. 다른 메서드는 현재 미지원이며, 구현 일정이나 모든 메서드의 지원을 약속하지 않는다.

## FR-046. 백엔드 목록과 분산

- 입력: 하나 이상의 HTTP 백엔드 목록과 전달 대상 요청.
- 동작: 요청마다 Round-Robin으로 다음 백엔드를 선택한다. HTTPS/TLS 백엔드는 이번 범위에서 제외한다.
- 결과·완료 기준: 백엔드가 하나면 그 백엔드로, 여러 개면 목록 순서로 돌아가며 전달한다. 구체적인 실행 인자 표현은 DS-052의 AI안이다.

## FR-047. 백엔드 연결과 재시도

- 입력: 해당 요청에 선택된 백엔드.
- 동작: 요청마다 새 TCP 연결을 만들고, 응답 중계를 끝내면 그 백엔드 연결을 닫는다. 연결 풀은 구현하지 않는다. 선택한 백엔드가 실패해도 다른 백엔드로 자동 재시도하지 않는다.
- 결과·완료 기준: 한 프록시 요청을 여러 백엔드에 재실행하지 않는다. POST의 중복 실행 위험을 피한다. 실패와 기한은 FR-051·053을 따른다.

## FR-048. 응답 스트리밍

- 입력: 백엔드에서 도착하는 응답 데이터.
- 동작: 응답 전체를 메모리에 모으지 않고 유한한 조각으로 받아 클라이언트에 중계한다.
- 결과·완료 기준: 큰 응답도 전체 크기에 비례해 메모리를 계속 늘리지 않는다. 느린 클라이언트의 읽기 제어·프레이밍 방식은 DS-048의 AI안으로 정리한다.

## FR-049. 클라이언트 연결과 기존 기능

- 입력: 클라이언트 연결과 프록시 요청 처리 결과.
- 동작: 클라이언트 keep-alive와 백엔드 연결 수명을 분리한다. 백엔드 연결을 닫는 것만으로 클라이언트 연결도 무조건 닫지 않는다. 프록시 경로 밖의 정적 파일 등 기존 기능은 유지한다.
- 결과·완료 기준: 같은 클라이언트 연결의 다음 프록시 요청에는 새 백엔드 연결을 사용한다. 백엔드에 보내는 Host는 선택 백엔드의 주소로 바꾼다. 불완전 응답 뒤에는 연결을 닫고, 정상 응답은 기존 클라이언트 재사용 조건을 적용한다.

## FR-050. 리다이렉트 주소 변환

- 입력: 백엔드 응답의 Location, 등록된 백엔드 목록, 실행 설정 PUBLIC_URL.
- 동작: 내부 백엔드를 가리키는 Location은 클라이언트가 우리 서버를 통해 접근하는 주소로 변환한다. 외부 사이트를 가리키는 Location은 변경하지 않는다. 내부·외부 구분에 예외 규칙을 둔다는 것은 사용자 결정이며 아래 세부 판정은 AI 설계안이다.
- 결과·완료 기준: 내부 백엔드로 직접 이동하지 않고 프록시 경유를 유지하며, 외부 로그인 사이트 등으로 이동하는 리다이렉트는 훼손하지 않는다.

세부 주소 판정·잘못된 Location 처리는 DS-050의 AI 설계안이다. 외부·상대 주소는 유지하고 HTML 본문·Set-Cookie를 일괄 치환하지 않는다. 변환 후 경로가 `/api` 밖이면 기존 정적 처리로 이어지므로 백엔드도 `/api` 경로 구조를 사용해야 한다.

## FR-051. 백엔드 기한 설정

- 입력: CLI/start.sh의 접속 제한·응답 무진행 제한.
- 동작: 초기 접속 제한은 5초, 응답 무진행 제한은 10초이며 실행 설정으로 바꾼다. 응답은 전체 총시간이 아니라 데이터 수신으로 갱신하는 무진행 기준이다.
- 결과·완료 기준: 정상적으로 계속 도착하는 긴 응답을 총 10초라는 이유로 중단하지 않는다. 수치는 사용자가 승인한 초기 설정이며 측정한 최적값이 아니다. 백엔드 송신·백프레셔 시 기한 운용은 DS-051의 AI안이다.

## FR-052. 시작 설정과 주소 해석

- 입력: 백엔드 목록, PUBLIC_URL, 시간 설정.
- 동작: 백엔드는 IP와 호스트 이름을 허용한다. 시작 시 DNS를 해석해 고정하고 변경 시 재시작한다. 잘못된 설정이나 DNS 해석 실패는 서버 시작을 중단한다.
- 결과·완료 기준: 일부 잘못된 백엔드를 조용히 제외하지 않는다. 주소 해석에 성공했지만 실제 서버가 꺼져 있는 것은 시작 실패가 아니라 요청 시 502로 처리한다. 요청 이벤트 루프에서 DNS 해석하지 않는다.

## FR-053. 실패 응답과 자원 정리

- 입력: 접속·응답 파싱·중계·시간 제한 결과.
- 동작: 접속 거절·비정상/불완전 응답은 502, 접속/응답 시간 초과는 504다. 클라이언트 최종 응답을 시작했다면 오류 응답을 덧붙이지 않고 닫는다.
- 결과·완료 기준: 정상 백엔드의 4xx·5xx는 그 상태로 중계하고 프록시 자체 실패와 구분한다. 성공·실패·단절·종료 모두 백엔드 소켓과 요청 자원을 정리한다. 실패한 POST를 재전송하지 않는다.

## 선택 이유와 트레이드오프 기록

아래는 확정 선택에 대한 **이번 문서의 AI 분석**이며, 사용자가 실제로 말한 이유를 복원한 기록이 아니다. 후속 설계에서 FR/DS와 함께 구체화한다.

| 선택·예시 | 얻는 점·추천 이유 | 대안과 감수할 비용 |
| --- | --- | --- |
| 경로 라우팅: `/api/users` | 현재 정적 파일 서버와 한 주소에서 공존하기 쉬움 | Host 라우팅과 달리 경로 영역을 나눠야 함 |
| 접두사·쿼리 유지 | 요청 대상을 그대로 추적하기 쉬움 | 접두사 제거 방식과 달리 백엔드도 `/api` 경로를 받아야 함 |
| HTTP 백엔드 | TLS 구현 없이 중계 기본 흐름에 집중 | 전송 구간 암호화는 제공하지 않음 |
| 요청별 Round-Robin | 단순한 다중 백엔드 분산 | 처리 속도·부하·상태를 반영하는 분산은 하지 않음 |
| 새 연결·자동 재시도 없음 | 풀 관리와 중복 실행 위험을 줄임 | 연결 생성 비용이 들고 선택 백엔드 실패를 다른 서버로 복구하지 않음 |
| 조각 스트리밍 | 전체 응답 적재보다 메모리를 제한하기 쉬움 | 송수신 속도 차이·부분 응답·실패 상태 관리가 필요함 |
| GET·POST부터 지원 | 현재 요청 수신 기능을 활용해 범위를 제한 | 다른 메서드가 필요한 백엔드 기능은 사용할 수 없음 |
| 내부 Location만 공개 주소로 변환 | 내부 백엔드로 직접 접속하는 문제를 줄이면서 외부 이동을 보존 | 원문 전달보다 주소 파싱·예외 검증이 복잡하며 미등록 별칭은 자동 변환하지 않음. 본문·쿠키 경로 문제까지 해결하지는 않음 |

## 검증 상태

`make all test sanitize`가 통과했다. 프록시 단위 검사는 모든 분할 위치의 chunk·헤더 경계, 중복/충돌 길이·제어 문자·크기 넘침·trailer 오류, 남은 수신 기한 보존, 접속/송신 기한 만료, 메모리 확보 실패, origin·호스트 이름·IPv6·Location 비교를 포함한다.

실제 TCP 백엔드 프록시 15개가 일반 빌드와 전체 서버 ASan·UBSan·누수 빌드에서 통과했다. 원문 경로/쿼리·1MiB 바이너리 POST·RR·새 연결·재시도 없음·Host/hop-by-hop·정상 500·CL/chunked/EOF·204/304·1xx/101·Location·기한·단절·FD·종료·프런트 keep-alive를 확인했다. 8MiB 응답과 수신 무진행 제한보다 긴 프런트 읽기 중단/재개, 다른 연결 병행 및 RSS 증가 제한도 검사했다.

기존 오류 TCP 12개·정적 파일 TCP 15개(일반 사용자)·동시 TCP 10개·keep-alive TCP 13개·POST TCP 13개가 통과했다. 마지막 upstream 감시 제거·임시 응답 타이머 분리 뒤 관련 3개를 일반 및 전체 서버 sanitizer로 다시 통과했다.

실제 패킷을 버리는 네트워크의 접속 기한 실험은 구성하지 않았으며 접속 기한 자체는 내부 시계 단위 검사로 확인했다. 처리량 부하 측정·TSan은 이번 단계에서 실행하지 않았다. EOF 경계의 조기 종료 판별과 전체 HTTP 준수에는 본 설계에 기록한 제한이 있다.

최종 Docker 이미지를 다시 빌드하고 이미지의 start.sh 실행·정적 200·미기동 백엔드 502·SIGTERM 정상 종료를 확인했다. 이 Docker 스모크는 성공 중계 검사가 아니며, 성공 중계는 위 실제 TCP 백엔드 검사에서 확인했다.
