## DS-044. 경로 기반 전달

입력은 파서의 원문 path다. `/api`와 정확히 같거나 `/api/`로 시작하는 경우만 프록시로 보낸다. 쿼리 유무와 빈 쿼리까지 보존해 백엔드 요청 대상을 재구성한다. `/%61pi`·`/apix`를 임의로 프록시 경로로 확대하지 않는다.
확인 기준은 접두사·쿼리 보존과 기존 정적 경로의 회귀다.

선택 이유: Host 라우팅보다 기존 정적 서버와 함께 쓰기 쉽고 원문 추적이 단순하다. 감수점은 백엔드도 `/api` 경로를 지원해야 하며 별도 URL 정규화 기능을 제공하지 않는 것이다.

## DS-045. 전달 메서드 범위

기존 검증을 통과한 GET·POST만 전달한다. POST는 기존 본문 상한·총수신 기한 아래 전체 본문을 받은 뒤 백엔드에 전송한다. 바이너리 길이를 사용하고 내용은 해석하지 않는다. 경로 밖 POST는 기존 204를 유지하고 다른 메서드는 기존 501이다.
Expect: 100-continue는 프록시가 기존 방식으로 처리하고 백엔드로 전달하지 않는다. 클라이언트 요청 chunked 지원은 추가하지 않는다.

선택 이유: 기존 수신 기능을 재사용해 중계 흐름에 집중한다. 대안인 요청 본문 즉시 스트리밍보다 단순하지만 요청별 본문 메모리와 백엔드 전달 전 대기 비용을 감수한다. 다른 메서드 지원 일정은 정하지 않는다.

## DS-046. 백엔드 목록과 분산

유효한 전달 요청을 시작할 때 목록의 다음 항목을 선택하고 RR 위치를 한 번 진행한다. 정적 요청·수신 검증 실패는 RR을 소비하지 않는다. 목록 항목 하나가 여러 IP로 해석돼도 RR 항목은 늘리지 않는 안이다.
확인 기준은 요청별 순서, 단일 백엔드 동작, 실패 후 다음 요청의 RR 순서다.

선택 이유: 부하 기반 분산·상태 탐지보다 단순하고 재현 가능하다. 응답 속도·가용성을 반영하지 않아 느리거나 꺼진 백엔드도 순서에 따라 선택되는 비용을 감수한다.

## DS-047. 백엔드 연결과 재시도

이벤트 루프가 non-blocking connect·send·recv를 epoll로 관리한다. EINPROGRESS 뒤 준비 이벤트에서 SO_ERROR로 접속 결과를 확인한다. 소켓 FD와 연결 세대·요청 순번을 묶고 부분 송신 오프셋과 EAGAIN을 처리한다. 파일 worker를 소켓 대기에 묶지 않는다.
요청마다 선택 백엔드에 한 번만 연결한다. DNS 결과가 여러 개면 시작 시 고른 첫 사용 가능 형식 주소를 고정 사용하는 안이며, 요청 실패 후 다른 주소·백엔드로 재접속하지 않는다. 응답이 끝나면 백엔드 소켓은 닫는다.

선택 이유: 연결 풀·자동 재시도보다 수명 관리가 단순하고 POST 중복 실행을 피한다. 새 TCP 연결 비용과 일부 일시 실패를 복구하지 못하는 비용을 감수한다.

## DS-048. 응답 스트리밍

백엔드 응답 헤더 전체를 검증·재구성하기 전에는 클라이언트로 전달하지 않는다. 헤더 상한은 기존과 같은 8192바이트, 데이터 조각은 8192바이트를 쓰는 AI안이다. 상태 줄·헤더 이름·값의 제어 문자·CRLF 경계·길이 충돌을 검사한다. 잘못된 헤더, 중복 CL, CL+TE, 잘못된 chunk 형식은 502 또는 최종 응답 시작 뒤 종료다.

지원할 응답 경계는 다음 AI안으로 제한한다.

| 백엔드 응답 | 중계 방식 |
| --- | --- |
| 유효한 Content-Length | 선언 길이만 중계. 미달 EOF는 실패, 초과를 다음 응답으로 처리하지 않음 |
| 최종 chunked만 사용하는 유효 TE | 유한 조각으로 해석·재인코딩. chunk 크기만큼 전체를 적재하지 않음 |
| 길이/TE 없는 본문 응답 | 백엔드 EOF까지 중계하고 프런트에는 chunked로 경계를 제공 |
| 1xx·204·304 등 본문 없는 응답 | 상태별 HTTP 규칙 적용. 204·1xx에 CL/TE를 생성하지 않음 |

지원하지 않는 전송 코딩 조합은 502다. chunk 크기·종료·유한 trailer 영역을 검사하며 trailer는 전달하지 않는 제한을 명시한다. chunked의 마지막 0조각은 정상 종료를 확인한 뒤에만 보낸다. 길이 없는 응답은 EOF가 경계이므로 원 서버의 의도치 않은 조기 종료를 완벽히 판별할 수 없다.
유효한 임시 1xx는 최종 응답과 별도 상태로 처리한다. 로컬에서 처리한 Expect 관련 100은 중복 전달하지 않고, 그 밖의 1xx는 검사 후 중계한다. 101은 터널/Upgrade 미지원이므로 502다. 임시 응답 누적 헤더량도 유한하게 제한한다. 임시 응답 송신과 최종 응답 시작 여부를 분리한다.

선택 이유: 전체 응답 버퍼링 대신 큰 응답의 메모리를 제한하고 빨리 전달한다. 대가는 상태기계·trailer 제한·중간 실패 처리이며, 응답을 이미 보낸 뒤 원래 상태를 다른 오류로 바꿀 수 없다.

## DS-049. 클라이언트 연결과 기존 기능

요청·응답 양방향에서 Connection 및 그 헤더가 지목한 필드와 Keep-Alive·Proxy-Connection·TE·Trailer·Transfer-Encoding·Upgrade 등 연결별 필드를 제거하고 현재 구간에 맞게 재구성한다. CL도 검증한 길이로 하나만 생성한다. 백엔드 요청은 Connection: close, Host는 설정 백엔드의 authority로 바꾼다. 콘텐츠 자체의 Content-Encoding 등 종단 간 정보는 임의로 바꾸지 않는다.
클라이언트가 제공한 Forwarded/X-Forwarded 계열을 신뢰 정보로 전달하지 않는 안이다. 새로운 전달 정보 생성은 이번 범위에서 제외하고 Via는 중계 구간을 나타내도록 생성한다. hop-by-hop 지목으로 Host나 framing 필드를 숨겨 검증을 우회하지 못하게 원래 목록부터 검사한다.
정상 백엔드의 4xx·5xx는 상태와 본문을 그대로 중계한다. 프런트의 재사용은 기존 정책·요청 수 상한·close 요청·종료 상태에 따른다. close-delimited 백엔드라도 변환한 응답 경계가 완성돼야 재사용한다.

선택 이유: 원문 통째 중계보다 헤더 처리는 많지만 서로 다른 연결 수명을 분리하고 경계 혼동을 막는다. 백엔드 전용 인증·쿠키·본문 내용을 자동 보정하는 기능까지 제공하지는 않는다.

## DS-050. 리다이렉트 주소 변환

PUBLIC_URL은 scheme·host·port로 이루어진 공개 origin으로 설정하고 클라이언트 Host에서 추정하지 않는다. 백엔드 Location을 URI 구조로 나누고 등록 백엔드의 HTTP host·port와 정확히 일치할 때만 공개 origin으로 바꾼다. 호스트 대소문자는 무시하고 생략 HTTP 포트는 80이다. 문자열 부분 일치·사설 IP 여부·추가 DNS 조회로 내부를 추정하지 않는다.
`//host/path`도 authority를 검사한다. 외부 주소·상대 주소는 유지하고 경로·쿼리·fragment는 보존한다. `/api`를 다시 붙이거나 HTML·Set-Cookie를 일괄 치환하지 않는다. 비정상 URI·제어 문자·중복 Location은 응답 검증 실패로 처리하는 AI안이다.
예: 등록 `127.0.0.1:8001`의 `http://127.0.0.1:8001/api/login?q=1`은 PUBLIC_URL의 같은 경로로 바꾸고 `http://127.0.0.1.evil.example:8001/...`는 외부로 유지한다. 변환 경로가 `/login`이면 기존 정적 처리로 간다는 한계를 명시한다.

선택 이유: 원문 전달과 달리 내부 주소 노출과 직접 이동을 줄인다. 외부 로그인 이동은 보존하지만 정확한 URI 파싱·설정 관리가 필요하고 미등록 별칭·쿠키 경로·본문 링크 문제는 해결하지 않는다.

## DS-051. 백엔드 기한 설정

CLOCK_MONOTONIC으로 접속 기한은 connect 시작부터 계산한다. 초기 5초다. 응답 무진행은 요청을 다 보낸 뒤 응답을 기다리는 시점에 시작하고 양수 recv마다 갱신한다. 초기 10초이며 응답 전체 총기한이 아니다.
백엔드 요청 송신도 무한히 기다리지 않도록 응답 무진행 설정값을 송신 무진행 기한에 재사용하는 **AI안**이다. 성공한 send마다 갱신하고 초과는 504다. 클라이언트 본문 수신·프런트 송신 제한은 기존 값과 구분한다.
출력 버퍼가 차면 백엔드 EPOLLIN을 잠시 내리고, 이 의도적 정지 동안 응답 수신 기한은 남은 시간을 보존해 멈춘다. 프런트 송신 무진행 기한은 계속 적용한다. 버퍼가 비어 읽기를 재개하면 보존한 잔여 시간으로 재개하며 매번 새 10초를 주지 않는다. 실제 수신 성공만 정상 갱신한다.

선택 이유: 총시간보다 긴 정상 스트리밍을 허용하고 느린 클라이언트 때문에 백엔드를 오판하지 않는다. 대가는 여러 기한의 상태 관리이며, 조금씩 계속 도착하는 응답은 오래 유지될 수 있다. 5초/10초는 측정 최적값이 아니다.

## DS-052. 시작 설정과 주소 해석

기존 아홉 인자 뒤에 PUBLIC_URL·접속 초·응답 무진행 초·백엔드 목록을 붙이는 CLI/start.sh 연장안을 사용한다. BACKENDS는 하나의 인자로 전달하는 쉼표 구분 HTTP origin 목록을 제안하며 IPv6는 대괄호 표기다. 환경 변수명·배치·목록 구분자는 AI 선택이다.
PUBLIC_URL은 경로 접두사·userinfo·쿼리·fragment 없는 공개 origin으로 검증한다. 백엔드에는 HTTP만 허용하고 IP·호스트명·포트를 검증한다. 시작 시에만 getaddrinfo를 수행해 주소를 보관하고 요청 중에는 DNS하지 않는다. 하나라도 잘못됐거나 해석이 실패하면 시작을 중단한다. 시작 시 실제 TCP 가용성 검사를 필수로 하지 않는다.
호스트 IP가 바뀌면 재시작한다. 설정한 origin의 이름은 Host·Location 비교에 보관하고, 해석한 IP를 임의의 추가 내부 별칭으로 등록하지 않는다.

선택 이유: 동적 DNS 갱신·별도 설정 파일보다 기존 실행 방식과 단일 이벤트 루프를 유지하기 쉽다. 대가는 재시작이 필요하고 긴 목록은 실행 인자가 길어지는 것이다. 공개 origin 검증과 TLS 종단 기능은 별개이며 TLS 기능은 추가하지 않는다.

## DS-053. 실패 응답과 자원 정리

접속 거절·TCP 응답 중단·검증 실패는 502, 접속/송신/응답 기한은 504다. 프록시 자체 메모리 확보 실패는 기존 500으로 처리하는 AI안이다. 백엔드의 정상 500을 프록시 실패 502로 바꾸지 않는다.
클라이언트 최종 응답 전이면 기존 상태명 오류 형식으로 응답한다. 최종 응답을 한 바이트라도 보낸 뒤 실패하면 연결만 닫는다. 로컬/백엔드 임시 1xx는 이 최종 응답 기준에 포함하지 않는다. 응답 생성·송신 실패를 반복 오류 응답으로 해결하지 않는다.
모든 경로에서 upstream epoll 등록·소켓·버퍼·타이머를 해제한다. 클라이언트 단절 시 upstream을 닫고, 늦은 이벤트는 세대/요청 순번으로 무시한다. 연결별 upstream은 최대 하나이며 유한 송수신 버퍼를 사용한다. 기존 연결 상한에 따른 추가 FD·버퍼 예산을 초기화 때 점검하고 실패 시 무한 재시도하지 않는다.
서버 종료는 기존 idle 즉시 종료·진행 요청 유예를 유지한다. 기한이 끝나면 양쪽 소켓을 닫으며 백엔드 풀·유휴 upstream은 만들지 않는다. 다른 요청의 FD나 worker 소유 메모리를 닫지 않는다.

선택 이유: 재시도와 오류 숨김보다 실패 원인과 중복 실행 여부가 명확하다. 대가는 일부 요청 실패를 그대로 사용자에게 전달하고 이미 시작한 응답은 불완전한 채 끝날 수 있다는 것이다.

## 검증 결과와 한계

`proxy_config.c`는 시작 origin/DNS·Location 비교를, `proxy.c`는 요청 재구성·upstream 소켓 I/O·응답 프레이밍·유한 출력을, `concurrency.c`는 양쪽 epoll·프런트 송신·요청 수명·기한 연결을 담당한다. 시작 CLI는 기존 아홉 인자 뒤 PUBLIC_URL·접속 초·응답 무진행 초·BACKENDS를 붙인 열세 필수 인자다.

`make all test sanitize`가 통과했다. `tests/test_proxy.c`는 chunk·임시/최종 헤더를 모든 분할 위치로 공급하고 잘못된 헤더·길이 충돌·크기 넘침·chunk/trailer 오류를 검사한다. 의도적 정지의 남은 기한 보존, 접속/송신 기한 만료, 프록시 할당 실패, DNS/IPv6 origin·내부/외부 Location 경계도 단위 검사했다.

`tests/test_proxy.py`의 실제 TCP 15개가 일반 빌드와 전체 서버 ASan·UBSan·누수 빌드에서 통과했다. 1MiB 바이너리 요청, RR·연결 수명·재시도 없음, CL/chunked/EOF와 204/304, 임시 응답 뒤 최종 오류, 정상 백엔드 500, 위조/잘못된 헤더, 내부/외부/상대/유사 호스트 Location, 송신 정지/응답 무진행·계속 진행하는 긴 응답, 시작 오류, 프런트 재사용·FD 회수·종료를 포함한다.

8MiB 응답에서 프런트 읽기를 백엔드 idle보다 길게 중단한 뒤 정상 재개하고 다른 연결이 진행되는지 확인했다. 프로세스 RSS 증가도 4MiB 미만으로 제한됨을 확인했다. 이 수치는 해당 테스트 조건의 관측 범위이며 처리량 측정이나 모든 부하의 메모리 상한 증명은 아니다. 출력 중 upstream 등록을 아예 제거해 HUP 반복 통지를 피하고 재개 시 재등록한다.

기존 오류 12개·정적 15개·동시 10개·keep-alive 13개·POST 13개 회귀도 통과했다. 마지막 감시/임시 응답 타이머 변경은 관련 실제 TCP 3개를 일반/전체 서버 sanitizer로 재검사했다. 접속 제한은 내부 시계 단위로 검사했으며 실제 SYN 드롭 환경의 기한 실험은 미실행이다. TSan·처리량 부하 측정도 미실행이다. 강제 프로세스 종료의 OS 자원 회수와 정상 종료 누수 검사는 구분한다.

최종 Docker 이미지를 다시 빌드하고 이미지의 start.sh 실행·정적 200·미기동 백엔드 502·SIGTERM 정상 종료를 확인했다. 이 Docker 스모크는 성공 중계 검사가 아니며, 성공 중계는 위 실제 TCP 백엔드 검사에서 확인했다.
