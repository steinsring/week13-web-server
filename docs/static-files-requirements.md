# 정적 파일 서빙 요구사항 명세

정적 파일 서빙은 **클라이언트가 파일 경로를 요청하면 서버가 파일 내용을 응답하는 기능**이다. 파일 업로드 기능이 아니다.
이번 요구 범위는 확정했다. 구현과 검증을 완료했다. 구현 방법은 [설계 명세](static-files-design.md)에 정리한다.

## 범위와 이전 단계 관계

이 단계를 적용하면 GET의 고정 `hello world` 응답을 파일 응답으로 대체한다. 기존 FR-001~014의 단계 기록은 유지한다.
GET 외 메서드 501, 미지원 버전 505, 헤더 수신 총 10초, 기존 오류 본문 정책, 응답 후 연결 종료, 한 연결씩 처리하는 방식은 유지한다.
HEAD·Range·캐시·압축·POST 본문·프록시·동시 처리·파일 업로드는 이번에 추가하지 않는다.

## FR-015. 파일 루트 지정과 서버 시작

- 입력: `./server 8080 ./public`처럼 포트와 파일 루트를 지정한 실행 인자.
- 동작: 지정 디렉터리를 파일 제공의 기준점으로 사용한다. 폴더가 없거나 사용할 수 없으면 오류를 출력하고 서버 시작을 중단한다. 자동 생성하지 않는다.
- 결과·완료 기준: 지정 루트로 시작하고, 잘못된 루트로는 시작하지 않는다.

## FR-016. URL 경로와 접근 제한

- 입력: 파서가 원문으로 보관한 요청 경로와 별도의 쿼리 문자열.
- 동작: 파일을 찾는 단계에서 경로의 퍼센트 인코딩을 한 번만 푼다. 쿼리는 파일명에 포함하지 않는다. 루트 밖으로 나가려는 경로는 403으로 거절한다.
- 결과: `/hello%20world.txt?q=1`은 루트 안의 `hello world.txt`를 찾는다. 파서의 원문 보존 정책은 유지한다.
- 완료 기준: 일반 경로와 인코딩된 경로 모두 루트 밖의 파일을 제공하지 않는다. 중간 경로·최종 파일·기본 페이지의 심볼릭 링크는 모두 403이다.

## FR-017. 기본 페이지와 디렉터리 이동

- 입력: `/`, `/docs/`, 실제 디렉터리인 `/docs` 등의 요청.
- 동작: `/`는 루트의 `index.html`, `/docs/`는 해당 디렉터리의 `index.html`을 찾는다. 기본 페이지가 없으면 404이며 목록은 보여주지 않는다. 실제 디렉터리 `/docs`는 301로 `/docs/`에 이동시킨다.
- 결과·완료 기준: 기본 페이지가 있으면 파일 응답, 없으면 404, 슬래시 없는 디렉터리는 올바른 Location을 받는다.

## FR-018. MIME 타입 결정

- 입력: 전송할 서버 파일의 확장자.
- 동작: 확장자에 맞는 Content-Type을 응답한다. 모르는 확장자도 전송하며 `application/octet-stream`을 사용한다.
- 결과·완료 기준: HTML·CSS·JS·이미지는 대응 타입을 받고, 알 수 없는 확장자도 원본 파일 내용을 받는다. 구체 매핑은 AI 설계 선택으로 아래 설계 문서에 기록한다.

## FR-019. 파일 응답 전송

- 입력: 루트 안에서 접근 가능한 일반 파일.
- 동작: 파일 내용을 HTTP 성공 응답으로 보낸다. 파일 크기에 맞는 Content-Length와 Content-Type을 제공한다.
- 결과·완료 기준: 텍스트와 바이너리 모두 원본 바이트와 일치하며 부분 송신도 처리한다. 응답 뒤 연결을 닫는다.

## FR-020. 오류 처리와 자원 정리

- 입력: 파일 탐색·열기·읽기·응답 전송의 처리 결과.
- 동작: 파일 없음, 접근 거절, 서버 내부 실패를 구분한다. 내부 절대 경로를 응답에 노출하지 않는다. 성공·실패 모두 파일·디렉터리·요청·연결 자원을 정리한다.
- 결과·완료 기준: 아래 설계 매핑에 맞는 오류 응답 후 다음 정상 요청을 처리할 수 있다. 응답 시작 후 실패하면 새 오류 응답을 이어 보내지 않는다.

## 결정과 검증 계획

루트 CLI 지정, 기본 페이지, 301 이동, 미지 확장자 전송, 한 번 디코딩, 쿼리 제외, 루트 탈출·심볼릭 링크 거절, 잘못된 루트로 시작 중단은 사용자 결정이다.
루트 인자 생략 정책, 세부 오류 매핑, 경로 정규화, MIME 표, 파일 열기·전송 방법은 [AI 세부 설계](static-files-design.md)로 구분한다.

다음 기준을 실제 테스트로 확인했다.

| 확인 대상 | 예상 결과 |
| --- | --- |
| 실제 HTML·CSS·JS·이미지·빈 파일 | MIME·길이·본문 바이트 일치 |
| `/`, `/docs/`, 기본 페이지 없음 | 각각 index.html 응답 또는 404, 목록 없음 |
| `/docs?q=1`이 실제 디렉터리 | 301, Location `/docs/?q=1` |
| `%20`, 이중 인코딩, 쿼리 포함 경로 | 한 번만 디코딩, 쿼리는 파일명에서 제외 |
| 일반·인코딩된 `..` 루트 탈출 | 403 |
| 중간·최종·index.html 심볼릭 링크 | 루트 안을 가리켜도 403 |
| 파일 없음·권한 거절·파일 I/O 실패 | 각각 404·403·500 또는 응답 시작 후 연결 종료 |
| 부분 송수신·클라이언트 단절·실패 후 재요청 | 자원 정리 후 다음 정상 연결 처리 |
| 없는 루트·사용 불가 루트 | 폴더 생성 없이 시작 중단 |

검증 결과: 파서 97개 검사, 응답 송신·읽기 실패 검사, 정적 응답·정리 2400회 검사와 sanitizer(주소·정의되지 않은 동작·누수) 검사 통과. 관리자 권한이 없는 Linux UID 65534에서 정적 파일 통합 테스트 15개가 통과했다. 서버 전체 부하 검사는 수행하지 않았다.

기존 오류 응답 TCP 회귀 12개도 통과했다. 정적 루트의 index.html을 기존 본문과 같은 바이트로 준비하고 HTML MIME으로 기대값을 갱신해 검사했다.
