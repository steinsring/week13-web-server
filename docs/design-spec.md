# 1단계 설계 명세

## 선택 이유와 트레이드오프

이 절은 최초 최소 구현의 선택을 설명한다. 당시 합의한 동작과 그 선택의 기술적 득실을 구분하며, 득실 분석 전체가 당시 사용자의 발언이었다는 뜻은 아니다. 이후 단계에서 대체한 정책은 당시 범위의 기록이다.

| 대응 설계 | 선택과 이유 | 비교 대안 | 얻는 점 | 감수한 점 |
| --- | --- | --- | --- | --- |
| DS-001 | 블로킹 소켓으로 한 연결씩 처리한다. 먼저 socket→bind→listen→accept 흐름을 이해하기 위한 최소 구현이다. | 처음부터 이벤트 루프나 스레드 도입 | 연결 흐름과 자원 소유자가 단순하다. | 느린 연결 하나가 다른 연결 처리를 지연시킨다. 동시 처리 단계에서 대체했다. |
| DS-002 | 수신 조각을 누적해 헤더 끝을 확인한다. TCP 수신 단위와 HTTP 요청 경계를 분리하기 위해서다. | recv 한 번으로 전체 요청이 온다고 가정 | 분할 수신에도 헤더 끝을 찾는다. | 누적 길이·한도 관리가 필요하고, 헤더 끝 확인만으로는 올바른 요청인지 알 수 없다. 파싱 단계에서 보완했다. |
| DS-003 | 항상 hello world를 보낸다는 사용자 선택으로 응답 형식을 고정했다. | 파일·경로별 응답부터 구현 | 소켓 송신과 HTTP 응답 구조에 집중한다. | 요청에 따른 실제 처리는 하지 못한다. |
| DS-004 | 응답 후 클라이언트 연결만 닫고 다음 연결을 기다린다는 사용자 선택이다. | 같은 연결에서 여러 요청 처리 | 요청 간 상태를 재사용할 필요가 없다. | 매번 TCP 연결을 다시 만들어야 한다. keep-alive 단계에서 대체했다. |

8080·listen backlog 16·헤더 한도 8192는 과제나 성능 측정으로 도출한 최적값이 아니다. 8080은 최초 실행 예시용 비특권 포트이고, 16은 초기 접속 대기열 예시이며, 8192는 무한 누적을 막는 유한 상한이다. 각각 포트 충돌 가능성, 접속 폭주 시 대기열 부족, 큰 헤더 거절이라는 비용이 있다. backlog는 처리 가능한 동시 연결 수와 다르다. 현재 실행 설정과 정책은 후속 단계 명세를 따른다.

이 문서는 [요구사항 명세](project-spec.md)를 **어떻게 구현할지** 정한다.
아래는 최초 요청·응답 단계의 설계다. 현재 코드는 서버·파서·응답 파일로 분리했으며, 요청 수신의 최신 설계는 [파싱 설계 명세](http-parser-design.md)를 따른다. 실행 방법과 파일별 역할은 [README](../README.md)에 정리한다.

다음 단계는 [HTTP 요청 파싱 설계 명세(초안)](http-parser-design.md)에서 다룬다.

## DS-001. 서버 시작과 연결 수락

대응 요구사항: [FR-001](project-spec.md#fr-001-서버-시작과-연결-수락)

1. `socket()`으로 연결을 기다릴 TCP 소켓을 만든다.
2. `bind()`로 지정 포트에 소켓을 연결한다.
3. `listen()`으로 연결을 받을 준비를 한다.
4. `accept()`로 클라이언트 연결을 수락한다.
5. 수락한 연결의 소켓을 요청 수신 단계에 넘긴다.

연결을 기다리는 소켓과 실제 요청·응답에 사용하는 클라이언트 소켓을 구분한다.

## DS-002. HTTP 요청 수신

대응 요구사항: [FR-002](project-spec.md#fr-002-http-요청-수신)

1. 클라이언트 소켓에서 `recv()`로 데이터를 받는다.
2. 받은 데이터를 누적하고, 헤더의 끝인 `\r\n\r\n`을 찾는다.
3. 아직 헤더 끝이 없으면 `recv()`를 반복한다.
4. 헤더를 모두 받으면 응답 전송 단계로 넘어간다.

한 번의 `recv()`로 요청 헤더 전체가 도착한다고 가정하지 않는다.
이번 단계는 본문 없는 GET 요청을 대상으로 한다.

## DS-003. HTTP 응답 전송

대응 요구사항: [FR-003](project-spec.md#fr-003-http-응답-전송)

1. 아래 형식의 고정 응답을 준비한다. `\r\n`은 HTTP의 줄바꿈을 뜻한다.

```text
HTTP/1.1 200 OK\r\n
Content-Type: text/plain; charset=utf-8\r\n
Content-Length: 11\r\n
Connection: close\r\n
\r\n
hello world
```

2. 헤더와 본문은 `\r\n\r\n`으로 구분한다. 본문 뒤에는 줄바꿈을 붙이지 않는다.
3. `send()`로 응답을 전송한다.
4. 일부만 전송되면 보낸 길이를 기록하고, 남은 부분을 계속 전송한다.
5. 응답 전체를 보내면 연결 종료 단계로 넘어간다.

## DS-004. 연결 종료와 다음 요청 대기

대응 요구사항: [FR-004](project-spec.md#fr-004-연결-종료와-다음-요청-대기)

1. 응답을 보낸 클라이언트 소켓을 `close()`로 닫는다.
2. 연결을 기다리는 서버 소켓은 유지한다.
3. 다시 `accept()`로 돌아가 다음 연결을 기다린다.

이 흐름을 반복하며, 한 번에 하나의 연결을 처리한다.

## 최소 구현의 기본값과 한계

- `main()`은 실행 인자로 포트를 받고, 생략하면 8080을 사용한다.
- `receive_request()`는 최대 8192바이트까지 헤더를 누적한다. 초과 또는 수신 실패 시 클라이언트 연결을 닫는다.
- 현재 `http_response.c`의 `http_send_hello()`는 고정 응답 전체를 전송한다. `SIGPIPE`를 무시해 연결 끊김으로 서버 전체가 종료되지 않게 한다.
- `recv()`와 `send()`가 `EINTR`로 중단되면 재시도한다.
- 초기화 실패 시 서버 소켓을 정리하고 종료한다. 프로세스 종료 시 남은 소켓은 OS가 회수한다.
- 최초 단계에서는 헤더 끝만 확인했다. 현재 요청 줄·헤더·Host 검증은 파싱 단계에서 추가했으며, 오류 HTTP 응답과 수신 타임아웃은 아직 구현하지 않았다.
- 연결 하나를 순서대로 처리하므로 불완전한 요청을 유지하는 클라이언트는 다음 연결 처리를 지연시킬 수 있다.
