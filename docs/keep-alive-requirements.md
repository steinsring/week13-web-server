# Keep-alive 요구사항 명세

이번 6단계는 **응답을 보낸 연결을 재사용해 다음 요청을 처리하는 기능**이다. 요구 범위를 구현했으며 아래 실행 검증 결과를 기록한다.
구현 방법은 [설계 명세](keep-alive-design.md), 이전 단계는 [POST 본문 요구사항](post-body-requirements.md)에 정리한다.

## 범위와 이전 단계 관계

기존 FR-001~036의 단계 기록을 유지하고, 응답마다 연결을 닫던 정책과 다음 요청 바이트를 버리던 정책을 이번 명세로 대체한다.
기존 GET 정적 파일·POST 수신 후 204·헤더/본문 경계 검사·시간 제한·연결 상한·파일 작업 제한은 유지한다. 다른 연결 사이의 동시성도 유지한다. 한 연결 안의 요청 병렬 처리, chunked 지원, 동적 처리·프록시는 추가하지 않는다.

## FR-037. 연결 재사용과 종료 요청

- 입력: HTTP/1.1 요청과 Connection 헤더.
- 동작: 기본적으로 응답 후 연결을 유지한다. 클라이언트의 Connection: close, 서버 제한이나 안전상 종료 사유가 있으면 응답 후 닫는다.
- 결과·완료 기준: 한 연결에서 GET·POST를 반복할 수 있다. 종료할 응답에는 Connection: close를 표시하고 재사용하지 않는다. POST 204의 본문·Content-Length·Transfer-Encoding 금지는 유지한다.

## FR-038. 순차 처리와 잔여 데이터

- 입력: 한 연결에서 이어지는 요청 바이트.
- 동작: 현재 요청의 최종 응답을 모두 보낸 뒤 다음 요청을 처리한다. 한 recv에 다음 요청까지 들어오면 남은 바이트를 유한 버퍼에 보관한다. 현재 응답 중에는 추가 읽기를 멈춰 무한 적재를 막는다.
- 결과·완료 기준: 연달아 온 GET·POST의 응답이 요청 순서와 일치한다. 본문 길이 뒤 다음 요청을 본문에 섞거나 버리지 않는다. 다른 연결은 동시에 처리된다.

## FR-039. 다음 요청 대기 시간

- 입력: 최종 응답 완료 시각과 설정한 idle 제한 시간.
- 동작: 응답 완료 후 다음 요청이 오지 않는 시간을 제한한다. 시간 초과 시 연결을 닫는다. 요청 수신을 시작한 뒤의 헤더·본문 수신 제한과 구분한다.
- 결과·완료 기준: 설정 시간 안의 다음 요청은 처리하고, idle 만료 연결은 회수한다. 보관한 다음 요청이 있으면 idle 상태로 기다리지 않는다. 세부 기한 전환은 설계 선택으로 기록한다.

## FR-040. 연결별 최대 요청 수

- 입력: 설정한 최대 요청 수 N과 연결별 처리 횟수.
- 동작: N번째 최종 응답은 Connection: close로 보내고 연결을 닫는다.
- 결과·완료 기준: N번째까지 처리하며 이후 보관된 요청은 시작하지 않는다. 100 Continue는 임시 응답이므로 요청 횟수를 추가하지 않는다.

## FR-041. 오류 뒤 재사용

- 입력: 요청 수신 완료 여부와 오류 응답 상태.
- 동작: 요청을 완전히 수신한 403·404 응답 뒤에는 연결을 재사용한다. 파싱 오류·수신 실패 등 요청 경계를 안전하게 확정할 수 없는 경우는 닫는다. 클라이언트의 close나 최대 요청 수 제한은 오류 뒤에도 적용한다.
- 결과·완료 기준: 같은 연결의 404 다음 정상 GET이 처리된다. 잘못된 요청 뒤에는 뒤따르는 요청을 실행하지 않는다.

500·503 등 나머지 오류의 세부 정책은 사용자 확정사항으로 기록하지 않는다. 이번 설계에서는 보수적으로 닫는 안을 제안한다.

## FR-042. 실행 설정

- 입력: CLI와 start.sh의 idle 제한 초·최대 요청 수.
- 동작: 두 값을 실행 설정으로 지정할 수 있게 한다. start.sh 초기 설정은 idle 10초·최대 100회이며 CLI로 변경 가능하다.
- 결과·완료 기준: 직접 실행과 스크립트 실행이 같은 값을 적용한다. 값 검증과 정확한 인자 배치는 설계에 구분한다.

## FR-043. 요청 자원과 서버 종료

- 입력: 응답 완료·요청 재사용·연결 종료·SIGINT/SIGTERM.
- 동작: 다음 요청 전에 이전 요청의 본문·헤더·파일 자원은 정리하되 소켓과 다음 요청 바이트는 유지한다. 닫힌 연결의 자원은 기존 수명 보장 방식으로 정리한다.
- 결과·완료 기준: 반복 요청의 데이터가 섞이지 않고 누수·중복 해제·늦은 작업 결과 오적용이 없다. idle 연결도 기존 유지 연결 상한에 포함한다. 종료 시 기존 유예를 넘겨 keep-alive 연결을 계속 남기지 않는다.

## 결정과 검증 상태

연결 내 순차 처리·기본 유지와 close 존중·잔여 데이터 보관·완전 수신 403/404 재사용·idle 및 횟수 설정·초기 10초/100회는 사용자 결정이다. 기타 오류 종료, 기한 전환, 버퍼 운용, 종료 중 새 요청 중단은 [AI 세부 설계](keep-alive-design.md)로 구분한다.
구현 후 `make all test sanitize`를 통과했다. 실제 keep-alive TCP 13개는 반복 GET/POST, 혼합·분할 파이프라인, 한 수신 조각을 넘는 연속 요청, 403/404·301 뒤 재사용, close 토큰, N번째 close와 100 횟수 제외, idle 회수와 다음 헤더 기한 분리, 연결 상한, 동시 진행, FD 회수, 종료 중 다음 요청 중단을 확인했다.
전체 서버의 ASan·UBSan·누수 검사로 같은 keep-alive 13개와 기존 POST 13개를 통과했다. 기존 오류 TCP 12개·정적 파일 TCP 15개·동시 TCP 10개도 최대 요청 수 1 설정으로 통과했다. 단위 검사는 파서 97개·정적 파일 2400개와 본문·응답·동시 상태 검사를 포함한다.
Docker 이미지를 실제 빌드하고 start.sh로 실행해 curl의 같은 연결 재사용과 SIGTERM 정상 종료를 확인했다. 처리량 부하 측정과 TSan 검사는 이번 단계에서 실행하지 않았다.
