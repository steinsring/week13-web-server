# 동시 요청 처리 요구사항 명세

여러 클라이언트의 연결을 유지하며 요청을 처리한다. 이번 범위를 구현했으며 아래 검증 결과를 기록한다.
구현 방법은 [설계 명세](concurrency-design.md), 이전 단계는 [정적 파일 요구사항](static-files-requirements.md)에 정리한다.

## 범위와 기술 조건

C와 pthread, Linux의 epoll을 결합한다. 외부 HTTP·이벤트 루프 라이브러리는 사용하지 않는다. Docker Linux에서 개발·검증하며, epoll 사용으로 이번 구현은 macOS에서 그대로 빌드할 수 없다. 다른 OS용 이벤트 처리 구현은 이번 범위가 아니다.
기존 순차 연결 처리를 아래 동시 처리 방식으로 대체한다. HTTP 파싱, 정적 파일·MIME·301, 루트 탈출·심볼릭 링크 거절, 기존 오류 응답, GET만 지원, 요청별 연결 종료는 유지한다.
POST 본문·프록시·keep-alive·파일 미리 읽기는 추가하지 않는다.

## FR-021. 이벤트 루프와 작업 스레드 역할

- 입력: 여러 클라이언트 연결과 파일 작업.
- 동작: 이벤트 루프는 연결 수락·요청 수신·파싱·응답 송신을 맡는다. 고정 개수의 작업 스레드는 파일 탐색·열기·읽기를 맡는다.
- 결과·완료 기준: 한 클라이언트의 수신·송신 대기나 파일 작업 때문에 이벤트 루프가 다른 연결 처리를 멈추지 않는다.

## FR-022. 실행 인자

- 입력: `./server 8080 ./public 4 64 100`처럼 포트·루트·작업 스레드 수·대기 작업 수 상한·유지 연결 수 상한을 순서대로 지정한다.
- 동작: 다섯 인자를 모두 필수로 받는다. 숫자 예시는 기본값이 아니다.
- 결과·완료 기준: 지정한 스레드 수와 각 상한으로 실행한다. 누락·잘못된 값·필수 자원 초기화 실패 시 오류를 알리고 시작하지 않는다.

## FR-023. 작업 대기열과 포화 처리

- 입력: 새 요청의 첫 파일 작업 또는 전송 중인 요청의 다음 읽기 작업.
- 동작: 대기열 상한은 아직 작업 스레드가 맡지 않은 작업 수다. 실행 중 작업은 제외한다. 새 요청의 첫 작업을 넣을 때 대기열이 꽉 차면 503 응답 후 닫는다.
- 결과: 이미 응답 중인 요청의 다음 읽기는 연결별 대기 상태로 보관한다. 빈자리가 생기면 재시도하며 이벤트 루프는 다른 연결을 계속 처리한다.
- 완료 기준: 대기열이 상한을 넘지 않고, 신규 포화는 503이다. 진행 중 응답에는 새 오류 응답을 붙이지 않으며 대기 중 무한 반복으로 CPU를 점유하지 않는다.

## FR-024. 파일 조각 전송

- 입력: 전송할 파일과 연결의 송신 진행 상태.
- 동작: 작업 스레드가 한 조각 읽기 → 이벤트 루프가 그 조각을 끝까지 송신 → 다음 읽기 순서로 반복한다. 파일 전체 적재나 다음 조각 미리 읽기는 하지 않는다.
- 결과·완료 기준: 큰 파일도 원본과 일치하고, 느린 클라이언트에게 보낼 조각이 무한히 쌓이지 않는다.

## FR-025. 유지 연결 수 제한

- 입력: 수신·작업 대기·파일 작업 중·송신 등 모든 상태의 유지 연결 수.
- 동작: CLI 상한에 도달하면 새 연결 수락 감시를 멈춘다. 기존 연결은 계속 처리하고, 자리가 생기면 수락 감시를 재개한다.
- 결과·완료 기준: 유지 연결 수가 상한을 넘지 않는다. 커널의 접속 대기열은 별개이며 포화 시 접속 지연·실패가 가능하다. 이 경우 HTTP 503을 보장하지 않는다.

## FR-026. 시간 제한

- 입력: 연결 수락·송신 진행·파일 작업 대기 시각.
- 동작: 다음 세 제한을 구분한다. 파일 작업 실행 시간은 작업 대기나 송신 무진행 시간에 포함하지 않는다.

| 구간 | 기준과 초과 시 처리 |
| --- | --- |
| 요청 헤더 수신 | 수락 직후부터 총 10초. 조각 수신으로 갱신하지 않는다. 초과 시 기존 408 응답을 시도하고 닫는다. |
| 송신 무진행 | 보낼 데이터가 준비된 송신 구간에서 10초 동안 성공한 송신이 없으면 닫는다. 실제 바이트를 보낸 send마다 기준을 갱신한다. 파일 전체 전송 시간 제한은 아니다. |
| 파일 작업 대기 | 작업을 기다리기 시작한 때부터 스레드가 맡기까지 10초. 대기열 등록을 기다리는 시간도 포함한다. 응답 바이트 전송 전이면 503을 시도하고 닫고, 이미 전송했으면 닫기만 한다. |

- 결과·완료 기준: 대기열 재시도나 EINTR로 기한이 연장되지 않는다. 작업을 맡으면 그 대기는 끝나며, 나중에 생긴 별도 읽기 작업은 새 대기로 측정한다.

## FR-027. 종료 유예

- 입력: SIGINT 또는 SIGTERM.
- 동작: 새 연결 수락을 멈추고, 이미 수락한 요청은 최대 10초 동안 마무리한다. 모두 끝나면 일찍 종료하고, 유예가 끝나면 남은 연결을 닫고 프로세스를 종료한다.
- 결과·완료 기준: 반복 종료 신호로 유예가 늘어나지 않는다. 남은 파일 작업 때문에 스레드 합류를 무한히 기다리지 않는다. 종료 중에도 기존 수신·송신·작업 대기 제한을 유지한다.

## FR-028. 연결별 자원과 실패 처리

- 입력: 동시 요청, 연결 단절, 작업 완료, 시간 초과, 종료.
- 동작: 요청·파일·전송 버퍼를 연결별로 관리한다. 다른 요청의 데이터가 섞이지 않게 한다. 닫힌 연결의 작업 결과를 새 연결에 적용하지 않는다.
- 결과·완료 기준: 중복 해제·이미 해제한 메모리 접근·다른 요청의 FD 닫기가 없다. 응답 시작 뒤 실패하면 두 번째 응답을 보내지 않는다. 개별 요청 실패 후 다른 정상 연결을 계속 처리한다.

## 결정과 검증 계획

위 역할 분담·CLI 상한·포화 처리·읽기 순서·시간 제한·종료 유예는 사용자 결정이다. epoll 운용 방식, 알림 큐, 조각 크기와 메모리 수명은 [AI 세부 설계](concurrency-design.md)에 구분한다.

동시 TCP 10개 검사와 기존 파서·응답·정적 파일·동시 상태 단위 검사 및 ASan·UBSan·누수 검사를 통과했다. 기존 오류 TCP 12개와 정적 파일 TCP 15개도 통과했다.
동시 TCP는 내용 일치, 느린 수신·송신 병행, 신규 큐 포화 503, 연결 상한·재개, 세 시간 제한, 단절·FD 재사용, 종료 유예·조기 종료·기한 종료를 포함한다.
후속 읽기 큐 포화·FIFO 재시도·대기 기한 유지·응답 시작 뒤 종료와 실행 중 객체 수명은 동시 상태 단위 검사로 확인했다.
전체 서버의 ASan·UBSan·누수 검사는 병렬·단절·큐 포화·정상 종료 4개 시나리오를 통과했다. TSan은 실행 환경의 `unexpected memory mapping`으로 시작에 실패해 경합 검증 미완료다. 처리량 부하 측정은 실행하지 않았다.
