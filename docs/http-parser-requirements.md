# HTTP 요청 파싱 요구사항 명세

이 문서는 **요청을 어떤 정보로 나누어 저장할지** 정한다.
구현 방법은 [파싱 설계 명세](http-parser-design.md)에 정리한다.
앞 단계의 [요구사항 FR-001~004](project-spec.md)는 유지한다.

이번 단계의 동작 범위를 구현했다. 파서와 소켓 서버를 분리하고, 단위 검사와 실제 TCP 요청 검증을 진행했다.

## 목표와 범위

HTTP 요청을 줄 단위로 해석하고, 결과를 서버의 요청 구조체에 저장한다.
첫 줄은 메서드·요청 대상·HTTP 버전으로, 이후 헤더는 이름·값으로 나눈다.
요청 대상에서는 경로와 쿼리 문자열을 구분한다.

본문 처리, 쿼리 내부의 `name=value` 해석, 퍼센트 인코딩 디코딩, 오류 HTTP 응답은 다음 단계로 미룬다.
터미널 출력이나 응답 내용 변경은 이번 요구사항에 포함하지 않는다.
C·POSIX 소켓·Docker Linux와 외부 HTTP 라이브러리 금지 조건은 앞 단계와 같다.

## FR-005. 요청 줄 파싱

- 입력: HTTP 요청의 첫 줄.
- 동작: 줄이 완성된 뒤 메서드, 요청 대상, HTTP 버전을 구분한다.
- 요청 줄은 `메서드 SP 요청대상 SP HTTP/1.1` 형식이다. `SP`는 ASCII 공백 한 개다. 항목은 비어 있으면 안 되며, 누락·추가 항목, 두 개 이상의 구분 공백, 탭 구분은 실패로 처리한다.
- 결과: 나눈 정보를 요청 구조체에 저장한다.
- HTTP 버전은 `HTTP/1.1`만 허용한다. 다른 버전은 파싱 실패로 처리하며, FR-008에 따라 응답 없이 해당 연결을 닫는다.
- 메서드는 `GET`, `POST` 등의 고정 목록으로 제한하지 않고, 문법에 맞는 이름을 원문 그대로 저장한다. 메서드의 실제 지원 여부 판단과 실행은 후속 처리 단계에서 다룬다.
- 메서드 이름은 하나 이상의 token 허용 문자로 구성되어야 한다. 허용 문자는 ASCII 영문자·숫자와 다음 기호다.

```text
! # $ % & ' * + - . ^ _ ` | ~
```

- 완료 기준: `GET /hello HTTP/1.1`에서 `GET`, `/hello`, `HTTP/1.1`을 구분해 확인할 수 있다. 데이터가 여러 번에 나뉘어 도착해도 결과가 같다.

## FR-006. 헤더 파싱

- 입력: 첫 줄 다음부터 헤더를 끝내는 빈 줄까지.
- 동작: 헤더를 한 줄씩 읽고, 모든 헤더의 이름과 값을 구분한다. 빈 줄을 만나면 헤더 파싱을 끝낸다.
- 결과: 특정 종류만 골라 저장하지 않고, 모든 헤더의 이름과 값을 요청 구조체에 저장한다.
- 완료 기준: `Host: localhost`와 `X-Test: sample`을 받으면 두 헤더 모두 이름과 값으로 구분해 확인할 수 있다.

같은 이름의 헤더가 여러 번 나오면 덮어쓰거나 합치지 않고, 각 줄의 이름과 값을 받은 순서대로 모두 저장한다.
예를 들어 `Accept: text/html`과 `Accept: application/json`은 두 항목으로 남긴다.
헤더 이름의 대소문자는 원문 그대로 저장한다. 이름으로 조회할 때는 대소문자를 구분하지 않으며, `Host`와 `host`는 같은 이름으로 취급한다. 헤더 값 전체를 소문자로 바꾸지 않는다.
헤더 값 앞뒤의 공백(SP)과 탭(HTAB)은 제거하고, 값 내부의 공백과 탭은 유지한다. 예를 들어 `X-Name:   hello world   `의 값은 `hello world`로 저장한다. 경로·쿼리·메서드나 헤더 이름에 이 제거 규칙을 일괄 적용하지 않는다.
헤더 이름은 메서드와 같은 token 허용 문자로 구성되어야 하며 비어 있으면 안 된다. `:` 누락, 이름과 `:` 사이 공백은 실패다. `Host:localhost`처럼 `:` 뒤 공백이 없어도 허용한다.

HTTP/1.1 요청은 `Host` 헤더가 정확히 한 줄 있어야 한다. 이름은 대소문자를 무시하고 세며, 없거나 두 줄 이상이면 값이 같더라도 실패로 처리한다. 값은 비어 있지 않은 `host[:port]` 형식인지 검사한다. 호스트 안의 공백이나 숫자가 아닌 포트 표기는 실패다. 대괄호로 둘러싼 IPv6 주소 표기도 허용한다.

`Content-Length`와 `Transfer-Encoding`은 이번에는 문자열로만 저장한다. 값, 중복, 두 헤더의 상호관계 검증은 본문 처리 단계로 미룬다. 따라서 `Content-Length: abc`도 이번 단계에서는 저장한다. 이는 완전한 HTTP/1.1 검증을 구현했다는 뜻이 아니다.

## FR-007. 경로와 쿼리 분리

- 입력: 요청 줄에서 얻은 요청 대상.
- 동작: 첫 `?`를 기준으로 앞은 경로, 뒤는 쿼리 문자열로 나눈다. `?`가 없으면 전체를 경로로 보고 쿼리는 없는 것으로 구분한다.
- 결과: 경로와 쿼리를 요청 구조체에 따로 저장한다. 쿼리는 원문 문자열로 보관한다.
- 완료 기준: `/search?q=c&page=1`은 경로 `/search`, 쿼리 `q=c&page=1`로 나뉜다. `/hello%20world`는 디코딩하지 않고 그대로 저장한다.

쿼리 내부의 `name=value` 해석과 디코딩은 사용하는 단계에서 필요할 때 처리한다.

## FR-008. 실패 처리와 기존 흐름 연결

- 입력: 수신 중이거나 파싱이 끝난 요청.
- 동작: 성공하면 기존 응답 흐름으로 이어진다. 잘못된 형식으로 파싱할 수 없으면 실패를 호출자에게 알린다.
- 결과: 성공 시 기존 `hello world` 응답을 유지한다. 실패 시 `main()`이 응답 없이 해당 연결을 닫고 다음 연결을 기다린다.
- 완료 기준: 정상 요청은 구조체 저장 후 기존 응답을 받는다. 버전이 빠진 `GET /` 같은 요청은 실패하며, 이후 새 연결의 정상 요청은 계속 처리할 수 있다.

`400 Bad Request` 등 오류 응답은 이번 단계에 추가하지 않는다.

요청마다 독립된 수신 버퍼와 요청 구조체를 사용한다. 파싱한 문자열은 별도로 복사하지 않고, 해당 요청의 버퍼 안을 가리키는 포인터로 보관한다. 버퍼는 요청 처리가 끝날 때까지 유지하고, 성공·실패 모두 처리 종료 시 정리한다.
헤더 이름·값 포인터 목록은 필요한 헤더 수에 따라 공간을 늘린다. 별도의 고정 헤더 개수 제한은 두지 않으며, 기존 8192바이트 수신 크기 제한은 유지한다. 목록에 할당한 메모리도 요청 처리 종료 시 해제한다.
여러 요청을 같은 버퍼에 덮어쓰지 않는다. 이후 동시 처리로 확장해도 요청별 버퍼를 분리한다. 이번 단계에 동시 처리 기능을 추가하는 것은 아니다.

## 결정과 설계 선택

**사용자가 결정한 내용:** 구조체 저장, 줄 단위 파싱, 모든 헤더 수신 순서 보관, 헤더 이름 원문 보존·대소문자 무시 조회, 값 앞뒤 SP·HTAB 제거, HTTP/1.1과 이번 문법 검사, 첫 `?`로 경로·쿼리 분리, 원문 유지, 실패 시 연결만 종료, 기존 응답 유지. 요청별 버퍼·문자열 포인터·가변 헤더 목록도 선택했다.

**기존 구현에서 이어받는 조건:** 8192바이트 제한을 유지하며 현재 `http_request.h`의 `HTTP_HEADER_LIMIT`으로 관리한다. 이 수치는 이번 명세에서 사용자가 새로 선택한 값이 아니다.

**AI의 세부 설계 선택:** 구조체 필드 배치, 쿼리 없음의 표현, 헤더 배열의 초기 용량·증가 단위는 [설계 명세](http-parser-design.md#요청-구조체와-메모리)에 구분해 기록한다. 사용자 요구 수치가 아니며, 구현 후 검증할 대상이다.

메서드 문자열을 구분하는 일과 그 메서드의 기능을 지원하는 일은 별개다. 이번 단계에 POST 본문 처리 등을 추가하지 않는다.

## 검증 상태

다음은 검증에 사용하는 입력 예시다. 예시의 요청 줄에는 별도 표시가 없으면 정상 `Host` 헤더가 있다고 가정한다.

| 입력 또는 상황 | 예상 결과 |
| --- | --- |
| `GET /hello HTTP/1.1` | 세 항목 저장 |
| `CUSTOM / HTTP/1.1` | 문법에 맞는 메서드 이름 저장, 지원 여부는 후속 판단 |
| `GET /`, `GET  / HTTP/1.1`, `GET / HTTP/1.1 extra`, 탭 구분 | 실패 후 연결만 종료 |
| `GET / HTTP/1.0` 또는 `G(ET / HTTP/1.1` | 버전 또는 메서드 문법 실패 |
| `Host:localhost` | 통과 |
| `: value`, `Bad Name: value`, `Host : localhost`, `Host localhost` | 헤더 이름 또는 구분 문법 실패 |
| `Host` 없음, `Host`와 `host` 두 줄 | 실패 |
| `Host: localhost`, `Host: localhost:8080`, `Host: [::1]:8080` | 형식 검사 통과 |
| `Host: local host`, `Host: localhost:abc` | 형식 검사 실패 |
| `X-Test: a`와 `x-test: b` | 원문 이름과 순서 보존, 대소문자 무시 조회 시 둘 다 확인 |
| `X-Name:   hello world   ` | 값 `hello world` 저장 |
| `/hello%20world?q=a%20b` | 인코딩 원문을 유지하며 경로·쿼리 분리 |
| `Content-Length: abc`, 중복 길이 헤더 또는 전송 인코딩 헤더 | 문자열 저장, 본문 관련 유효성 판단은 다음 단계 |
| 요청 줄·헤더·CRLF가 여러 수신으로 분리됨 | 한 번에 수신한 경우와 같은 결과 |
| 성공·수신 실패·파싱 실패·할당 실패·전송 실패 | 요청 자원 정리 후 다음 연결 처리 |

IPv6 `Host` 표기를 읽는 것과 IPv6 소켓으로 연결받는 것은 별개다. 기존 IPv4 리스닝은 유지한다.
Docker GCC 빌드, 파서 96개 검사와 AddressSanitizer·UndefinedBehaviorSanitizer·누수 검사, 실제 TCP 기능 테스트 8개가 통과했다. 파서 메모리 검사에는 초기 할당·배열 확장 실패를 주입하는 경우도 포함한다. 전체 서버 부하 테스트는 실행하지 않았다.
