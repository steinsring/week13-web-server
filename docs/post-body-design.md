# POST 본문 수신 설계 명세

## 선택 이유와 트레이드오프

아래는 본문 수신 단계의 선택과 기술적 득실 분석이다. 사용자 선택과 AI 세부 구조의 구분은 기존 본문을 따른다. 모든 경로의 204는 애플리케이션 처리 성공이 아니라 이 단계의 수신 완료 정책이다. 초과 데이터 폐기·연결 종료는 이후 keep-alive 단계에서 잔여 데이터 보관으로 대체했다.

| 대응 설계 | 선택과 이유 | 비교 대안 | 얻는 점 | 감수한 점 |
| --- | --- | --- | --- | --- |
| DS-029 | 모든 POST 경로에서 수신 완료 후 204만 보낸다. | echo·JSON 처리·DB·CGI를 함께 구현 | 본문 수신과 애플리케이션 실행을 분리해 먼저 경계를 검증한다. | 경로별 실제 동작이 없으며 저장한 본문은 요청 정리 시 사라진다. |
| DS-030 | Content-Length 기반 경계만 지원하고 유효한 chunked는 501로 거절한다. | chunked 디코더도 함께 구현 | 미리 길이를 검사하고 정확한 수신 완료 지점을 정한다. | 길이를 미리 모르는 스트리밍 클라이언트를 지원하지 못한다. |
| DS-030 | 중복 CL은 값이 같아도, CL+TE도 거절한다. | 같은 값 병합·한 헤더를 우선해 수용 | 경계 해석의 모호함을 줄이고 단일 판정 경로를 유지한다. | 정규화해 받아들일 수도 있는 일부 요청까지 거절하는 보수적 정책이다. |
| DS-031 | 선언 길이만큼 요청별 메모리를 확보하고 바이트·길이로 보관한다. | 문자열 저장·임시 파일·조각별 스트리밍 처리 | NUL·바이너리를 보존하고 이후 처리가 전체 본문을 쉽게 사용할 수 있다. | 큰 본문·동시 POST만큼 메모리가 필요하다. 연결 상한×본문 한도가 커질 수 있고 전역 본문 메모리 예산은 없다. |
| DS-031 | 헤더 파서가 소비한 길이를 반환한다. | 수신 덩어리 전체를 헤더로 전달·헤더 뒤 데이터 폐기 | 같은 recv의 헤더·본문을 정확히 나누고 본문이 헤더 한도에 포함되지 않는다. | 호출자가 소비량과 잔여 바이트를 관리해야 한다. |
| DS-032 | 헤더 완료부터 고정 총기한을 두고 실행 설정으로 조절한다. | 마지막 수신 때마다 기한 연장 | 소량 전송으로 무한 점유하는 요청도 제한하고 헤더 대기와 구분한다. | 꾸준히 보내는 정상 요청도 총기한을 넘으면 실패한다. 본문 기한은 고정 10초가 아니라 별도 설정이며 스크립트 30초는 AI 예시다. |
| DS-033 | Expect를 요청하면 사전 검사 후 100을 최종 응답과 별도로 보낸다. | 항상 본문을 바로 받기·Expect 미지원 | 클라이언트가 기다리는 경우 큰 본문을 전송하기 전 거절할 수 있다. | 대기 왕복과 부분 임시 응답 상태가 추가된다. Content-Length는 길이 정보이고 Expect는 전송 전 확인 절차라는 역할 차이가 있다. |
| DS-034 | 경계·크기·기한·할당 오류를 구분한다. | 모두 400이나 연결 종료로 통합 | 클라이언트가 실패 원인을 구별하고 기존 오류 응답을 재사용한다. | 최종 응답 시작 여부와 임시 응답 상태에 따라 별도 처리가 필요하며 전달 성공은 보장하지 못한다. |
| DS-035 | CLI 검증을 유지하고 start.sh로 설정을 모은다. | 매번 긴 명령 입력·별도 설정 파일 파서 | 설정을 읽고 바꾸기 쉽고 기존 CLI를 활용한다. | 위치 인자는 여전히 많고 다른 환경에는 셸이나 Docker가 필요하다. 별도 설정 파일 형식은 제공하지 않는다. |
| DS-036 | 본문 수신은 루프가 논블로킹으로 수행하며 파일 worker를 사용하지 않는다. | POST 수신 동안 worker 하나를 할당 | 느린 POST가 파일 worker를 점유하지 않는다. | 루프가 복사와 수신 상태를 관리하며 과도한 단일 연결 수신량을 제한해야 한다. |

## DS-029. POST 완료 응답과 경로 범위

- 입력: 헤더 검사와 본문 수신을 완료한 POST.
- 처리: 파일 작업 큐에 넣거나 경로별 실행하지 않고 최종 204 응답을 준비한다. 204 전용 형식으로 상태 줄, Connection: close, 헤더 끝만 보낸다.
- 결과·확인 기준: 204에는 본문·Content-Length·Transfer-Encoding을 넣지 않는다. 기존 일반 오류·파일 헤더 작성기의 길이 헤더를 그대로 적용하지 않는다.

## DS-030. 본문 길이와 헤더 검증

- 입력: 원문을 유지한 헤더 목록.
- 처리: 헤더 이름을 대소문자 무시로 조회해 CL·TE를 모두 센다. CL+TE와 중복 CL은 먼저 400으로 거절한다. 헤더 값 바깥 공백 제거 후 CL은 ASCII 숫자만 허용하고, 곱셈·덧셈 전에 표현 범위를 검사한다.
- 결과·확인 기준: 빈 값·부호·쉼표·숫자 외 문자·지원 정수 표현 범위 초과는 400이다. 표현 가능한 정상 숫자를 비교해 POST 본문 상한 초과는 413이다. 길이 계산이 넘치지 않는다.

TE는 중복 줄을 수신 순서의 코딩 목록으로 검사한다. 잘못된 목록·chunked 중복·chunked가 최종이 아닌 경우를 포함한 문법·경계 오류는 400이다. 유효하게 chunked로 끝나는 목록은 디코더가 없으므로 501이다. 디코딩 구현은 추가하지 않는다.

기존 요청 줄·Host 등 오류 검사를 유지하고, 본문 경계 검증을 마친 뒤 메서드별 처리로 넘어간다. GET의 유효한 양수 CL은 본문 상한과 관계없이 400이다. GET 길이 0은 기존 정적 처리, POST는 상한 검사 후 수신, 나머지 문법 유효 메서드는 기존 501이다. 이 순서는 여러 오류가 겹칠 때 판정을 일관되게 하기 위한 설계 선택이다.

## DS-031. 본문 보관과 경계

- 입력: recv로 받은 바이트와 헤더 파서가 소비한 바이트 수.
- 처리: 파서가 헤더 끝까지 정확히 몇 바이트 소비했는지 호출자에게 돌려주는 인터페이스를 설계한다. 헤더 뒤의 동일 수신 데이터는 버리지 말고 바로 본문 수신기로 넘긴다. 헤더 한도에는 헤더 끝까지만 센다.
- 결과·확인 기준: 헤더와 큰 본문이 같은 recv에 있어도 본문 때문에 431이 되지 않는다. CRLFCRLF가 나뉘어 도착해도 경계 바이트가 중복되거나 누락되지 않는다.

요청별로 body 포인터·선언 길이·수신 길이를 보관한다. 양수 길이는 검증 후 필요한 메모리를 확보하고, 0이면 할당 없이 완료한다. memcpy와 명시적 길이를 사용하며 strlen·문자열 종료 표시에 의존하지 않는다. 길이만큼 정확히 저장한 뒤 수신을 마친다.
같은 recv에 붙은 초과 바이트는 저장·실행하지 않는다. 커널에 남아 있는 추가 데이터를 새로운 요청으로 읽어 실행하지도 않는다. 이번에는 파이프라이닝·keep-alive용 잔여 버퍼를 구현하지 않는다.

## DS-032. 본문 수신 기한

- 입력: 헤더 완료를 확인한 CLOCK_MONOTONIC 시각과 CLI 초 단위 값.
- 처리: 헤더 완료 시 본문 종료 기한을 한 번 계산한다. epoll 대기·읽기 전후에 만료를 확인하며, 조각 수신·EINTR·100 송신으로 갱신하지 않는다. 헤더와 함께 온 본문도 같은 기한 아래 처리한다.
- 결과·확인 기준: 기한 안에 선언 길이를 채우면 완료하고, 기한까지 미완성이면 최종 408을 준비한다. 0 길이는 즉시 완료한다. 초→시간 표현 변환도 범위를 검사한다.

기존 헤더 총 10초는 헤더가 완성되면 끝난다. 본문 수신 중에는 본문 총기한을 사용한다. 임시·최종 응답의 송신에는 기존 송신 무진행 제한을 적용하되, 본문 기한 자체는 송신 중에도 연장하지 않는다.

## DS-033. Expect 처리

- 입력: 모든 Expect 헤더와 헤더·길이 검증 결과.
- 처리: 대소문자를 무시해 100-continue만 지원한다. 그 밖의 기대는 417이다. 사전 검증과 본문 메모리 확보 실패가 있으면 100 대신 최종 오류를 준비한다. 받을 본문이 없거나 이미 모두 받은 경우에는 불필요한 100을 생략하는 설계다.
- 결과·확인 기준: 필요한 임시 응답은 `HTTP/1.1 100 Continue`와 빈 줄이며 본문·길이·전송 인코딩 헤더는 없다. 최종 204·오류와 별도로 송신한다.

100의 버퍼·송신 오프셋과 최종 응답의 버퍼·송신 바이트 수를 분리한다. EAGAIN·부분 송신을 처리하며, 100을 보냈다는 이유로 최종 응답이 시작됐다고 판단하지 않는다. 본문 수신은 임시 송신 상태와 별도로 진행할 수 있다.
100 일부를 이미 보낸 뒤 본문 오류가 나면 임시 응답을 완성한 후 최종 오류를 보낸다. 두 응답의 바이트를 섞지 않는다. 아직 100을 한 바이트도 보내지 않았으면 취소하고 최종 오류를 보낼 수 있다. 송신 불가·송신 기한 초과는 연결 정리로 끝낸다.

## DS-034. 실패 응답

- 입력: 경계 검증·본문 수신·할당·임시 송신 결과.
- 처리: [FR-034의 매핑](post-body-requirements.md#fr-034-실패-응답)을 기존 상태명 응답에 추가한다. 미달 EOF는 400, 본문 미완성 기한은 408, 할당 실패는 500이다.
- 결과·확인 기준: 100 뒤에도 최종 오류를 보낼 수 있다. 최종 응답을 이미 보내기 시작했거나 상대에게 쓸 수 없으면 새 응답을 덧붙이지 않고 닫는다.

413은 Content Too Large, 417은 Expectation Failed를 사용한다. 오류 본문은 상태명만 담고 기존 Content-Type·Content-Length·Connection: close 방식을 따른다. 오류를 준비한 뒤 본문 수신 타이머를 끝내 최종 오류를 반복 생성하지 않는다.

## DS-035. CLI와 실행 스크립트

- 입력: 기존 다섯 인자와 BODY_LIMIT·BODY_TIMEOUT.
- 처리: 일곱 위치 인자를 필수로 검증한다. 본문 최대 바이트와 총수신 초는 양의 정수로 받고, 저장·계산 범위와 할당 크기를 검사하는 세부 설계다. 누락 기본값은 넣지 않는다.
- 결과·확인 기준: start.sh의 PORT·ROOT·WORKERS·QUEUE_LIMIT·CONNECTION_LIMIT·BODY_LIMIT·BODY_TIMEOUT 변수를 따옴표로 보호해 같은 순서로 전달하고 exec로 서버를 실행한다. 공백 있는 ROOT도 한 인자로 전달하며 종료 신호가 서버에 전달된다.

스크립트 초기 예시 `8080`, `./public`, `4`, `64`, `100`, `1048576`, `30`은 AI 예시 설정이다. 사용자가 고정한 수치가 아니며 변경 가능하다. 별도 설정 파일 파서는 만들지 않는다. start.sh에서 이 값을 수정해 실행할 수 있다.

## DS-036. 기존 기능과 자원 정리

- 입력: 동시 연결과 본문 수신·응답·단절·종료 이벤트.
- 처리: 이벤트 루프가 non-blocking 수신 상태를 헤더→본문→최종 응답으로 확장한다. 요청 객체는 고정 위치에 유지하고 메모리는 요청 정리 경로에서 해제한다. POST 완료는 파일 worker 작업 없이 처리한다.
- 결과·확인 기준: 연결별 본문이 독립적이고 다른 GET·POST가 진행된다. 모든 성공·오류·시간 초과·종료 경로에서 메모리를 한 번만 해제한다. 기존 작업 중 객체 수명과 세대 번호 검사는 유지한다.

느린 대형 수신이 이벤트 루프를 독점하지 않도록 연결별 한 회 수신량을 유한하게 제한하는 설계다. 최대 연결 수와 본문 상한의 조합에 따라 메모리 사용이 커질 수 있으며, 할당 실패는 500으로 처리한다. 별도 전역 본문 예산은 추가하지 않는다.

## 검증 계획과 한계

다음 표는 확인 기준이다. 본문 단위 검사는 바이트 보존·분할 경계·할당 실패를, 동시 상태 단위 검사는 100의 부분 송신·EINTR·EAGAIN 뒤 최종 오류 순서를 확인했다. `make all test sanitize`가 통과했다. 실제 TCP POST 13개 시나리오는 일반 빌드와 전체 서버 ASan·UBSan·누수 검사 빌드 모두 통과했다. Docker 이미지 빌드와 이미지 안의 start.sh 실행·POST 204 응답도 확인했다. 표의 모든 항목에 독립적인 고장 주입을 수행했다는 뜻은 아니며, CLI 상한별 처리량 측정은 수행하지 않았다.

| 검증 대상 | 확인할 결과 |
| --- | --- |
| 모든 POST 경로·빈 본문·0 길이 | 완료 후 204, 본문·Content-Length·TE 없음 |
| 헤더+본문 한 번 수신·분할 경계·바이너리 NUL·개행 | 정확한 바이트·길이 보존, 헤더 8192바이트 한도와 본문 한도 분리 |
| 잘못된 CL·같은 값 중복·쉼표·정수 범위 초과·CL+TE | 400, 계산 넘침 없음 |
| 정확한 상한·상한보다 큰 정상 길이 | 각각 수신 가능·413 |
| 잘못된 TE·최종 코딩이 chunked 아님·유효 chunked | 각각 400·400·501 |
| 미달 EOF·기한 경계·조각 전송·할당 실패 | 400·408·고정 기한 유지·500, 단절 시 안전한 정리 |
| Expect 대기·알 수 없는 기대·100 부분 송신·100 후 본문 오류 | 필요한 100·417·순서 보존·최종 오류 가능 |
| 선언 길이 뒤 추가 데이터 | 본문에 미포함, 다음 요청 미실행, 응답 후 종료 |
| 동시 GET/POST·느린 전송·종료 신호 | 기존 기능·제한·유예 유지, 본문 자원 정리 |
| 직접 CLI·start.sh·잘못된 인자 | 동일 설정, 정확한 단위, 시작 전 검증 |

추가 데이터를 남긴 채 연결을 닫으면 TCP RST 등으로 클라이언트가 최종 응답을 온전히 관측하지 못할 수 있다. 추가 데이터 시나리오는 서버의 응답 생성·송신 시도와 클라이언트가 실제 관측한 종료를 구분해 기록한다. 전송 성공을 무조건 보장했다고 보고하지 않는다.
기존 파서·오류·정적 파일·동시 처리 회귀와 ASan·UBSan·누수 검사도 포함한다. 다음 keep-alive 단계에서 남은 바이트와 요청 재사용을 별도 설계한다.
