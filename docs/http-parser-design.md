# HTTP 요청 파싱 설계 명세

이 문서는 [파싱 요구사항 명세](http-parser-requirements.md)를 **어떻게 구현할지** 정리한다.
앞 단계의 [설계 DS-001~004](design-spec.md)는 유지하며, 요청 수신 부분에 파싱을 연결한다.
`server.c`, `http_request.c/.h`, `http_response.c/.h`로 분리해 구현하고 검증했다.
사용자가 확정한 동작과 AI가 선택한 세부 설계를 구분해 기록한다.

## DS-005. 요청 줄 파싱

대응 요구사항: [FR-005](http-parser-requirements.md#fr-005-요청-줄-파싱)

- 입력: `recv()`가 받은 임의 길이의 데이터 조각.
- 처리: 데이터를 누적하고 `\r\n`이 나올 때까지 한 줄이 완성되기를 기다린다. 첫 번째 완성된 줄에서 메서드, 요청 대상, HTTP 버전을 구분해 저장한다.
- 결과: 요청 구조체에 요청 줄의 정보가 채워진다.
- 확인 기준: 요청 줄이나 `\r\n`이 여러 수신에 걸쳐 나뉘어도 한 번에 도착한 경우와 같은 결과가 나온다.

`recv()` 한 번이 한 줄을 반환한다고 가정하지 않는다. 한 번에 여러 줄이 오면 완성된 줄을 순서대로 처리하고, 남은 불완전한 줄은 다음 수신 데이터와 이어 붙인다.
분리한 버전 문자열이 `HTTP/1.1`과 정확히 일치하는지 검사한다. `HTTP/1.0` 등을 포함해 일치하지 않으면 실패를 반환한다.
첫 줄에서 ASCII 공백 두 개의 위치를 찾아 정확히 세 항목으로 나눈다. 빈 항목, 추가 항목, 중복 공백, 탭 구분은 실패다.
메서드는 [요구사항의 token 허용 문자](http-parser-requirements.md#fr-005-요청-줄-파싱)로만 구성되는지 검사한 뒤 원문 그대로 저장한다. 지원 메서드 목록으로 거르지 않으며, 기능 실행은 후속 단계다.

## DS-006. 헤더 파싱

대응 요구사항: [FR-006](http-parser-requirements.md#fr-006-헤더-파싱)

- 입력: 요청 줄 이후에 완성된 각 줄.
- 처리: 빈 줄이면 헤더 끝으로 판단한다. 나머지 줄은 첫 `:`를 기준으로 헤더 이름과 값을 구분해 저장한다.
- 결과: 요청 구조체에서 모든 헤더의 이름과 값을 확인할 수 있다.
- 확인 기준: 값 안에 `:`가 있어도 첫 구분자 뒤의 값에 포함된다. 빈 줄 뒤의 데이터는 헤더로 파싱하지 않는다.

이 단계에서 `Content-Length` 같은 헤더의 값을 저장해도 요청 본문을 수신·해석하는 기능까지 구현하지는 않는다.
같은 이름의 헤더도 각각 독립된 항목으로 추가하고 수신 순서를 유지한다. 기존 값을 덮어쓰거나 쉼표로 합치지 않는다.
헤더 이름은 수신한 대소문자를 보존한다. 이름 조회는 대소문자를 무시해 비교하고, 같은 이름인 모든 항목을 수신 순서대로 확인할 수 있게 한다. 헤더 값 자체는 소문자로 변환하지 않는다.
첫 `:` 뒤의 값에서 선행·후행 SP와 HTAB만 제외한 범위를 저장한다. 값 포인터를 시작 위치에 맞추고 끝에 `\0`을 넣는 방식으로 처리할 수 있다. 내부 공백·탭과 문자 대소문자는 유지하며, 그 밖의 문자를 공백으로 취급해 제거하지 않는다.
헤더 목록을 받은 뒤 이름을 대소문자 구분 없이 비교해 `Host` 줄 개수를 확인한다. 정확히 한 줄이 아니면 파싱 실패를 반환한다. `Host: a`와 `host: a`도 두 줄로 세며, 이름·값이 같아도 하나로 합쳐 통과시키지 않는다.
첫 `:`가 없거나 이름이 비었거나 이름에 token 외 문자가 있으면 실패다. 따라서 이름과 `:` 사이 공백도 실패하고, `:` 뒤 공백이 없는 경우는 통과한다.

`Host`는 값의 바깥 SP·HTAB을 제거한 뒤 `host[:port]` 형식을 검사한다. 호스트 이름·IPv4 표기는 URI host 문법에 따라 읽고, IPv6 주소는 대괄호 범위와 주소 형식을 검사한다. 포트 표기가 있으면 숫자 표기를 검사한다. 이번 설계에서 별도의 포트 수치 범위를 추가하지 않는다. DNS 조회나 실제 접속은 하지 않는다.
IPv6 `Host` 검사에는 POSIX `inet_pton()`을 사용하는 방식을 제안한다. 이는 기존 IPv4 리스닝을 바꾸는 기능이 아니다.

`Content-Length`·`Transfer-Encoding`의 값·중복·상호관계는 검사하지 않고 각각 문자열로 저장한다. 그 밖의 헤더별 의미 검증이나 완전한 URI·HTTP 검증을 이번 단계에 추가하지 않는다.

## DS-007. 경로와 쿼리 분리

대응 요구사항: [FR-007](http-parser-requirements.md#fr-007-경로와-쿼리-분리)

- 입력: 요청 대상 문자열.
- 처리: 첫 `?`의 위치를 찾는다. 있으면 앞을 경로, 뒤를 쿼리로 저장한다. 없으면 요청 대상 전체를 경로로 저장한다.
- 결과: 경로와 쿼리 문자열이 구분된다. 쿼리에 다시 `?`가 나와도 그 뒤를 재분리하지 않는다.
- 확인 기준: `/hello%20world?q=a%20b`에서 경로는 `/hello%20world`, 쿼리는 `q=a%20b`로 남는다.

`%20` 등을 다른 문자로 바꾸거나, 쿼리를 `name=value` 목록으로 바꾸지 않는다.

## DS-008. 실패 처리와 기존 흐름 연결

대응 요구사항: [FR-008](http-parser-requirements.md#fr-008-실패-처리와-기존-흐름-연결)

- 입력: 클라이언트 연결과 파싱 결과를 담을 요청 구조체.
- 처리: `main()`이 호출하는 `serve_client()`에서 요청을 초기화하고 `receive_request()`로 수신·파싱한다. 성공하면 `http_send_hello()`를 호출한다. 실패하면 응답 전송을 건너뛴다.
- 결과: 성공하면 기존 `hello world` 응답 후 연결을 닫는다. 실패하면 응답 없이 연결만 닫는다. 두 경우 모두 다음 `accept()`로 돌아간다.
- 확인 기준: 실패한 요청의 일부 데이터가 다음 요청에 남지 않고, 다음 정상 요청을 처리할 수 있다.

기존 8192바이트 한도를 `HTTP_HEADER_LIMIT`으로 유지하며, 수신 실패 시 연결 종료 흐름도 유지한다. `recv()` 임시 공간 4096바이트는 AI가 선택한 한 번의 수신 크기이며 전체 요청 한도와 별개다.

## 요청 구조체와 메모리

사용자는 요청별 버퍼를 유지하고 각 문자열을 포인터로 참조하는 방식을 선택했다. 헤더 포인터 목록은 필요할 때 용량을 늘린다.

다음 필드 배치와 수치는 **AI가 선택한 세부 설계**이며 사용자 지정 요구사항이 아니다. 구현 후 검증할 대상으로 둔다.

| 요청 구조체 필드 제안 | 용도 |
| --- | --- |
| `buffer[8193]` | 기존 최대 8192바이트와 문자열 끝 표시용 1바이트를 요청별로 소유 |
| `method`, `version`, `path`, `query` | 각각 요청 버퍼 안을 가리키는 문자열 포인터 |
| `headers` | 이름·값 포인터 쌍을 담는 동적 배열 |
| `header_count`, `header_capacity` | 사용 중인 항목 수와 확보한 항목 수 |
| `used`, `line_start` | 누적 길이와 현재 줄 시작. 받은 바이트를 한 번씩 확인하므로 별도의 `scanned` 필드는 사용하지 않음 |
| `request_line_done`, `result` | 첫 줄 처리 여부와 미완료·완료·실패 상태 |

길이·개수·위치 값은 `size_t`로 관리하는 설계다. 쿼리가 없으면 `query = NULL`, `/path?`처럼 비어 있는 쿼리는 빈 문자열을 가리키게 한다. 원본 요청 대상 전체를 별도 복사하지 않고 경로·쿼리로 보관한다.

헤더 배열은 처음 필요할 때 8항목을 확보하고, 부족하면 용량을 두 배로 늘리는 방식을 선택한다. 별도의 헤더 개수 제한은 추가하지 않는다. 용량 계산의 정수 범위를 확인하고, 할당 실패는 요청 실패로 처리한다.

`realloc()` 결과는 임시 포인터로 받는다. 성공한 경우에만 배열 포인터와 용량을 바꾸고, 실패하면 기존 할당을 유지해 공통 정리 경로에서 해제한다.
배열이 이동해도 문자열 포인터는 고정된 요청 버퍼를 가리키므로 유지된다. 요청 버퍼 자체는 처리 중 이동하지 않는다. 내부 포인터가 이전 버퍼를 가리키므로, 파싱된 요청 구조체를 단순 값 복사해서 이동하지 않는다.

`main()`이 연결마다 요청 구조체를 초기화하고, 수신·파싱 함수에 그 주소를 전달한다. 수신 함수가 반환해도 요청 버퍼는 응답 처리가 끝날 때까지 남는다.
구분자 위치에 `\0`을 넣어 각 항목을 C 문자열로 구분할 수 있다. 이는 문자열 내용의 대소문자나 퍼센트 인코딩은 보존하지만, 수신한 바이트 전체를 변경 없이 보존하는 방식은 아니다.

메모리 소유권은 다음 원칙으로 관리한다.

- 요청 처리 동안 구조체가 가리키는 저장 공간을 유효하게 유지한다.
- 수신 함수의 지역 버퍼를 가리키는 포인터만 남긴 채 함수를 끝내지 않는다.
- 헤더 동적 배열은 요청 구조체가 소유하고, 요청 처리 종료 시 정리한다. 실패 시에도 이미 확보한 목록을 해제한다.
- 다음 요청을 시작할 때 이전 요청의 데이터가 남지 않게 한다.
- 응답 전송 등 요청 정보를 사용하는 작업이 끝나기 전에 버퍼를 재사용하거나 해제하지 않는다.
- 성공·수신 실패·파싱 실패·전송 실패 모두 요청 정리 경로를 거친다. 정리 이후에는 해당 버퍼를 가리키던 포인터를 사용하지 않는다.
- 향후 동시 처리 시 각 요청에 별도 구조체와 버퍼를 제공한다. 전역 버퍼 하나를 모든 연결이 공유하지 않는다.

## 검증 범위와 한계

파서 API는 `http_request_init()`·`http_request_feed()`·`http_request_next_header()`·`http_request_destroy()`다. 파서는 소켓 호출 없이 받은 바이트만 해석하므로 독립적으로 검사할 수 있다.
요청 줄·헤더·Host 검사, 모든 두 조각 수신 경계, 1바이트 수신, 8192바이트 경계, 중복 헤더, 요청별 데이터 분리와 할당 실패를 포함한 파서 96개 검사가 통과했다. 파서의 AddressSanitizer·UndefinedBehaviorSanitizer·누수 검사도 통과했다.
실제 TCP 기능 테스트 8개로 정상·잘못된 요청, 실패 후 다음 연결, 불완전한 요청 대기·연결 종료를 확인했다. 전체 서버 부하 테스트는 수행하지 않았다.

메서드 기능 실행, 요청 본문, `Content-Length`·`Transfer-Encoding`의 유효성, 오류 응답, 전체 URI·HTTP 문법 지원은 이번 범위 밖이다. 이 파서가 완전한 HTTP/1.1 검증을 수행한다고 보지 않는다.

token 문자 기준은 [RFC 9110 §5.6.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-5.6.2), Host 형식 참고는 [RFC 3986 §3.2.2–3.2.3](https://www.rfc-editor.org/rfc/rfc3986.html#section-3.2.2)다. 이 참고 문서 전체를 이번 단계의 지원 범위로 삼지는 않는다.
